## #1 🔴 Docker Hub 不可达 (GFW)

### 现象

```text
Error response from daemon: failed to resolve reference "docker.io/library/mysql:8.0":
  dial tcp 199.96.58.85:443: i/o timeout
```

`docker pull` 或 `docker compose pull` 拉取基础镜像时超时。

### 根因

服务器在中国大陆网络环境，`registry-1.docker.io` 被 GFW 封锁或 DNS 污染。

### 解决方案

**方案 A：配置 Docker 镜像加速器（推荐）**

```bash
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json <<-'EOF'
{
  "registry-mirrors": ["https://docker.m.daocloud.io"]
}
EOF
sudo systemctl daemon-reload
sudo systemctl restart docker
```

已知可用镜像源：

| 源 | 地址 | 状态 |
|----|------|------|
| DaoCloud | `https://docker.m.daocloud.io` | ✅ 可用 |
| 中科大 | `https://docker.mirrors.ustc.edu.cn` | ⚠️ 有时超时 |
| 网易 | `https://hub-mirror.c.163.com` | ✅ 可用 |
| 阿里云 | `https://registry.cn-hangzhou.aliyuncs.com` | ❌ 需登录 |
| 交大 | `https://docker.mirrors.sjtug.sjtu.edu.cn` | ❌ TLS 错误 |

**方案 B：逐张拉取（避开 referrer 检查）**

`docker compose pull` 的 referrer 检查在某些镜像站会超时。逐张 `docker pull <镜像名>` 可绕过。

### 验证

```bash
docker pull mysql:8.0  # 应成功返回
```

## #2 🔴 ghcr.io 镜像拉取需 Token

### 现象

```text
Error response from daemon: denied: access forbidden
```

### 根因

`ghcr.io`（GitHub Container Registry）需要认证才能拉取私有仓库的镜像。

### 解决方案

1. 在 GitHub 创建 Personal Access Token：
   - 打开 https://github.com/settings/tokens
   - **Fine-grained token** → `ghcr-pull`
   - Repository access: `Only select repositories` → 选 `fkeu520/cloudplatform`
   - Permissions: **Contents: Read**
2. 服务器登录：

```bash
echo <你的GitHubToken> | sudo docker login ghcr.io -u fkeu520 --password-stdin
```

### 验证

```bash
docker pull ghcr.io/fkeu520/cloudplatform/platform-user:latest
```

## #3 🟡 Docker Compose `build: []` 语法不兼容

### 现象

```text
validating /opt/platform/docker-compose.ghcr.yml:
  services.platform-workflow.build must be a string
```

### 根因

新版 Docker Compose v2.20+ 不再接受 `build: []`（空数组）语法，只接受字符串（`build: .`）或 null。

`docker-compose.ghcr.yml` 中的写法：

```yaml
services:
  platform-user:
    build: []  # ❌ 语法错误
    image: ghcr.io/...
```

### 解决方案

```bash
sed -i '/build: \[\]/d' docker-compose.ghcr.yml
```

删除所有 `build: []` 行，因为 ghcr.yml 只使用预构建镜像，不需要 build。

## #4 🔴 端口 9090 被 snap Prometheus 占用

### 现象

```text
failed to bind host port 0.0.0.0:9090/tcp: address already in use
```

### 根因

Ubuntu 系统预装了 snap 版本的 Prometheus（`/snap/prometheus/86/bin/prometheus`），默认监听 9090 端口。

### 排查

```bash
sudo ss -tlnp | grep 9090
# 输出: users:(("prometheus",pid=38167,fd=8))

sudo lsof -i :9090
ps -ef | grep prometheus
```

### 解决方案

```bash
# 停用 snap prometheus
sudo snap stop prometheus
sudo snap disable prometheus

# 或强制杀进程
sudo kill -9 <PID>

# 或完全移除
sudo snap remove prometheus
```

### 注意事项

其他端口也可能被预装服务占用：

| 端口 | 服务 | 平台容器 |
|------|------|---------|
| 9090 | snap Prometheus | platform-prometheus |
| 3000 | Grafana | platform-grafana |
| 9000 | MinIO | platform-minio |

## #5 🔴 Nacos cgroup v2 NullPointerException

### 现象

Nacos 容器反复重启，日志：

```java
Caused by: java.lang.NullPointerException: null
  at jdk.internal.platform.cgroupv2.CgroupV2Subsystem.getInstance(CgroupV2Subsystem.java:81)
  ...
  at io.micrometer.core.instrument.binder.system.ProcessorMetrics.<init>(ProcessorMetrics.java:76)
```

### 根因

- Nacos v2.2.3 镜像内置 JDK 17
- 服务器使用 cgroup v2（通过 `cat /proc/filesystems | grep cgroup2` 确认）
- JDK 17 + Micrometer 在 cgroup v2 环境有 bug，`ProcessorMetrics` 初始化时 NullPointerException

### 解决方案

**方案 A：降级到 JDK 8 版本的 Nacos（推荐）**

```bash
sed -i 's|nacos/nacos-server:latest|nacos/nacos-server:v2.1.2|g' docker-compose.yml
docker compose up -d nacos
```

v2.1.2 使用 JDK 8，不受 cgroup v2 bug 影响。

**方案 B：禁用 Container Support**

```bash
docker run -d -e JAVA_OPTS="-XX:-UseContainerSupport" ... nacos/nacos-server:latest
```

### 版本对照

| Nacos 版本 | JDK 版本 | cgroup v2 | MySQL 支持 |
|-----------|---------|-----------|-----------|
| v2.3.2 | 17 | ❌ 有 bug | ✅ |
| v2.2.3 | 17 | ❌ 有 bug | ✅ |
| v2.2.0 | 8 | ✅ | ✅ |
| v2.1.2 | 8 | ✅ | ⚠️ 需要 MYSQL_SERVICE_* 参数 |

## #6 🟡 Nacos 连接 MySQL - No DataSource set

### 现象

```text
Caused by: java.lang.IllegalStateException: No DataSource set
  at com.alibaba.nacos.config.server.service.repository.extrnal.ExternalStoragePersistServiceImpl
```

### 根因

Nacos v2.1.2 配置了 `SPRING_DATASOURCE_PLATFORM=mysql` 但缺少或不兼容某些数据源参数。

### 解决方案

**单机部署直接用内置 Derby（最简单）**：

```bash
# 删除所有 MySQL 数据源配置
sed -i '/SPRING_DATASOURCE_PLATFORM/d' docker-compose.yml
sed -i '/MYSQL_SERVICE_HOST/d' docker-compose.yml
sed -i '/MYSQL_SERVICE_DB_NAME/d' docker-compose.yml
sed -i '/MYSQL_SERVICE_PORT/d' docker-compose.yml
sed -i '/MYSQL_SERVICE_USER/d' docker-compose.yml
sed -i '/MYSQL_SERVICE_PASSWORD/d' docker-compose.yml
```

单机环境 Derby 足够，无需 MySQL 持久化。集群部署才需要 MySQL。

**集群部署需要 MySQL**：

```yaml
# 正确配置（Nacos v2.2.0+）
environment:
  MODE: cluster
  SPRING_DATASOURCE_PLATFORM: mysql
  MYSQL_SERVICE_HOST: mysql
  MYSQL_SERVICE_DB_NAME: platform_nacos
  MYSQL_SERVICE_PORT: 3306
  MYSQL_SERVICE_USER: platform
  MYSQL_SERVICE_PASSWORD: platform123
```

### 验证

```bash
docker logs platform-nacos | grep "Nacos started"
```

## #7 🟡 Nacos AUTH_TOKEN 必须设置

### 现象

```text
env NACOS_AUTH_TOKEN must be set with Base64 String.
exit 255
```

### 根因

Nacos entrypoint 脚本 `bin/docker-startup.sh` 在启动时检查 `NACOS_AUTH_TOKEN` 变量是否存在，即使 `NACOS_AUTH_ENABLE=false`。

### 解决方案

```bash
# 给一个合法的 Base64 字符串
docker run -d \
  -e NACOS_AUTH_ENABLE=false \
  -e NACOS_AUTH_TOKEN=$(echo -n "placeholder-secret-key" | base64 -w0) \
  ...
```

或在 `docker-compose.yml` 中：

```yaml
environment:
  NACOS_AUTH_ENABLE: false
  NACOS_AUTH_TOKEN: cGxhY2Vob2xkZXItc2VjcmV0LWtleQo=  # "placeholder-secret-key" 的 base64
```

## #8 🔴 后端服务连不上 MySQL - localhost 陷阱

### 现象

日志显示 MySQL 连接被拒绝：

```text
Caused by: java.net.ConnectException: Connection refused
  at com.mysql.cj.protocol.a.NativeSocketConnection.connect(NativeSocketConnection.java:62)
  ...
```

### 根因

`application.yml` 中各服务的 datasource URL 写的是 `localhost:3306`。在 Docker 容器中，**`localhost` 指向容器自身**，不是宿主机，也不是 MySQL 容器。

### 解决方案

在 `docker-compose.prod.yml` 中用环境变量覆盖：

```yaml
platform-user:
  environment:
    - SPRING_DATASOURCE_URL=jdbc:mysql://mysql:3306/platform?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&useSSL=false
```

`mysql` 是 Docker Compose 的服务名，Docker DNS 会自动解析到 MySQL 容器的 IP。

> **规则**: 容器内连接其他容器必须用 Compose 服务名（`mysql`、`redis`、`nacos`），不能用 `localhost`。

### 涉及服务

| 服务 | 数据库 | 需要覆盖 |
|------|--------|---------|
| platform-user | platform | ✅ |
| platform-auth | platform | ✅ |
| platform-ops | platform | ✅ |
| platform-workflow | platform | ✅ |
| platform-message | platform_message | ⚠️ 不同库名 |
| platform-gateway | 无 | ❌ 排除了 DataSourceAutoConfiguration |

## #9 🔴 Gateway 无法解析 nacos 主机名

### 现象

```text
Caused by: java.net.UnknownHostException: nacos
  at java.net.InetAddress.getAllByName0(InetAddress.java:988)
```

### 根因

`docker run` 手动创建的 Nacos 容器与 `docker compose` 创建的 gateway 容器**不在同一个 Docker 网络**，或 Nacos 容器没有注册 DNS 别名。

`docker run` 创建的容器只加入 `platform_default` 网络，但不会被 Docker Compose 的 DNS 服务发现。Gateway 通过 `lb://platform-user`（服务发现）或 `nacos:8848`（直连）访问 Nacos，如果 DNS 解析不到 `nacos` 主机名就会失败。

### 解决方案

**所有容器必须用同一方式创建：全部用 `docker compose` 管理。**

```bash
# 停止手动创建的容器
docker rm -f platform-nacos

# 用 docker compose 统一创建
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml -f docker-compose.prod.yml up -d
```

### 原理

Docker Compose 会自动创建 `platform_default` 网络，并用 Compose 服务名注册 DNS 别名。
- `platform-nacos` 容器注册为 `nacos`（service name）
- `platform-gateway` 可通过 `nacos:8848` / `nacos:9848` 访问

## #10 🟡 GELF 日志驱动 DNS 解析失败

### 现象

```text
docker compose up -d 报错 driver failed programming external connectivity
```

容器创建时 GELF log driver 无法解析 `logstash:12201`。

### 根因

Docker Desktop 内置 DNS 在某些网络配置下无法解析 Compose 服务名。Linux 服务器上通常正常。

### 解决方案

**临时：改用 json-file**

```yaml
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
```

**持久：切换到服务器部署**（Linux Docker 无此问题）。

## #12 🟡 UFW 端口开放语法

### 现象

```bash
sudo ufw allow 8080 8083 9411
# ERROR: Need 'to' or 'from' clause
```

### 根因

UFW 一次只能添加一个端口。要开放多个端口必须逐条执行：

```bash
sudo ufw allow 8080
sudo ufw allow 8083
```

或循环：

```bash
for port in 8080 8083 9411 9090 3000; do sudo ufw allow $port; done
```

### 需要开放的端口

| 端口 | 服务 | 说明 |
|------|------|------|
| 8080 | platform-admin | 管理后台 |
| 8090 | platform-ops-admin | 运营后台 |
| 8083 | platform-gateway | API 网关 |
| 8848 | platform-nacos | 注册中心控制台 |
| 9411 | platform-zipkin | 链路追踪 |
| 9090 | platform-prometheus | 指标采集 |
| 3000 | platform-grafana | 监控看板 |
| 5601 | platform-kibana | 日志查看 (内网) |

## #13 🟡 容器启动顺序依赖

### 现象

后端服务（gateway/user/auth 等）在 Nacos 还没完全就绪时就尝试连接 Nacos，报 `Connection refused`。

### 根因

Docker Compose 的 `depends_on` 默认只保证"已启动"，不保证"已就绪"。

```yaml
# ❌ 只等启动
depends_on:
  - nacos

# ✅ 等健康检查通过
depends_on:
  nacos:
    condition: service_healthy
```

### 解决方案

关键依赖加 `condition: service_healthy`：

```yaml
depends_on:
  mysql:
    condition: service_healthy
  nacos:
    condition: service_healthy
```

当前 compose.yml 中后端服务已全部配置 `condition: service_healthy`，但 Nacos 自身的 healthcheck 需要足够的 `start_period` 和 `retries`：

```yaml
healthcheck:
  test: ["CMD-SHELL", "curl -fs http://127.0.0.1:8848/nacos/v1/console/health/readiness"]
  interval: 15s
  timeout: 10s
  retries: 10
  start_period: 40s
```

## 附：部署流程检查清单

### 首次部署

```bash
# 1. 服务器准备
sudo ufw allow 8080 8083 9411 9090 3000
sudo sysctl -w vm.max_map_count=262144

# 2. Docker 配置
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json <<-'EOF'
{
  "registry-mirrors": ["https://docker.m.daocloud.io"]
}
EOF
sudo systemctl restart docker

# 3. 登录 ghcr.io
echo <token> | sudo docker login ghcr.io -u fkeu520 --password-stdin

# 4. 拉代码
git clone https://github.com/fkeu520/cloudplatform.git /opt/platform
cd /opt/platform && git checkout feat/m6-p1-1-trace

# 5. 创建 .env
cat > .env <<'CMDEOF'
MYSQL_ROOT_PASSWORD=<your-password>
MYSQL_PASSWORD=<your-password>
CMDEOF

# 6. 拉镜像 + 启动
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml -f docker-compose.prod.yml --env-file .env pull
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml -f docker-compose.prod.yml --env-file .env up -d

# 7. 验证
curl -s http://localhost:8083/actuator/health
```

### 日常更新

```bash
cd /opt/platform
git pull
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml -f docker-compose.prod.yml --env-file .env pull
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml -f docker-compose.prod.yml --env-file .env up -d
```

### 重启全部服务

```bash
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml -f docker-compose.prod.yml --env-file .env restart
```

### 查看日志

```bash
# 单个服务
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml -f docker-compose.prod.yml logs -f platform-gateway

# 所有服务
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml -f docker-compose.prod.yml logs --tail 30
```
