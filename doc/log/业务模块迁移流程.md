# 业务模块迁移流程规范

> **制定日期**: 2026-06-25
> **版本**: v1.0
> **适用范围**: csyh 业务模块向当前项目迁移（空间管理 → 企业档案 → …）
> **设计原则**: 页面级粒度 + 忠实 Copy 与 Adapt 分离 + 中间确认关卡
> **依据**: park-space 迁移复盘（9 个质量问题，P0 ClassCastException / parkId 错误绑定 / UI 风格不一致等）

---

## 迁移七步法

```
步骤1 ─→ 步骤2 ─→ 步骤3 ─→ 步骤4 ─→ 步骤5 ─→ 步骤6 ─→ 步骤7
 读需求    看代码    定页面    找依赖    确认理解    copy代码   融合调整
                               ⤷ 4.5 标注清单                      ⤷ 门禁
```

### 步骤 1 — 读需求文档

**目的**: 业务意图优先于代码理解，避免"代码怎么写就怎么理解"

**操作**:
- 阅读 `doc/产品需求说明书*.md` 中对应模块章节
- 如有产品原型图一并参考
- 产出：对该模块业务功能的一句话概括

### 步骤 2 — 查看代码结构

**目的**: 迁移前清楚目标项目的目录/代码/数据库规范，避免风格不匹配

**操作**:
- 当前项目后端：`code/platform-server/park-*/` 目录结构、Controller/Service/Mapper 模式
- 当前项目前端：`code/platform-admin/src/views/park/` 页面结构、api 调用模式
- 数据库表结构：当前项目中对应表 DDL 或 Flyway 迁移脚本
- 重点关注：分页格式、响应结构、异常处理、校验方式、UI 组件风格

### 步骤 3 — 确定第一个需要迁移的页面内容

**目的**: 页面级粒度推进，单页完成后再推进下一页，问题暴露范围可控

**操作**:
- 从用户视角确定一个完整功能页面（列表页 / 详情页 / 编辑页）
- 一次只移一个页面，不跨页
- 该页面的后端 API 可能涉及多个表/多个 Service，但入口页面只有一个

### 步骤 4 — 查找所有与该页面功能相关的依赖代码文件

**目的**: 迁移前理清每个实体/API 的依赖树，避免实体关系错绑

**操作**:
- 页面 → API 调用 → Controller → Service → Mapper → Entity → 表
- 前端组件、路由、API 定义文件一并列出
- 跨模块调用也要标注（如调了 park-common、platform-common）

#### 步骤 4.5（可选但推荐）— 标注代码改造清单

在依赖清单中标注每个文件的处理方式：

| 文件 | 处理方式 | 说明 |
|------|---------|------|
| `RoomController.java` | 直接 copy | 逻辑独立，只改包名 |
| `RoomService.java` | 需要改造 | `((Number) obj)` → `ServiceUtils.toLong` |
| `Room.java` | 需要改造 | 去掉 parkId 字段 |
| `RoomPurposeController.java` | 需要改造 | parkId 错误绑定需修正 |

**核心原则**：步骤 6 只做忠实 copy，改造在步骤 7 按清单进行，二者严格分离。

### 步骤 5 — 跟用户确认对业务的理解

**目的**: 关键关卡，避免理解偏差白做

**操作**:
- 向用户阐述当前页面涉及的业务逻辑
- 说明在当前项目下的改造方案
- 用户确认后再进入步骤 6

### 步骤 6 — 将 csyh 下相关代码直接 copy 过来

**目的**: 忠实复制，改包名/导包即可。改造与 copy 分离，便于溯源

**操作**:
- 从 csyh 源码把步骤 4 清单中的文件 copy 到当前项目对应目录
- 只做包名/命名空间/import 改写，不改业务逻辑
- 如 csyh 中该文件涉及类型转换强转（`((Number) obj)`），暂不改

### 步骤 7 — 根据当前项目进行融合调整

**目的**: 基于步骤 5 确认的方案做针对性改造

**操作**:
- 按步骤 4.5 标注的改造清单逐项修改
- 类型转换安全化（`((Number) obj)` → `ServiceUtils.toLong/toInt`）
- 字段修正（去掉错误绑定的 FK，补全校验注解）
- 响应格式统一（使用 `PageResult` / `Result.ok()`）
- 前端 API 对接、路由注册、菜单配置

## 质量门禁（每页完成后执行）

每完成 1 个页面的融合调整后，必须跑以下命令，全部通过才能进入下一页：

```bash
# 后端编译
rtk mvn compile -pl park-space -am

# 后端测试
rtk mvn test -pl park-space -am

# 前端构建
rtk vite build
```

## 部署流程

```
Windows 编辑 commit → push（双平台） → CI 构建 → 217 docker compose pull + up
```

- **禁止本地构建镜像**（遵从 `doc/ops/CI_CD操作手册.md` 强约束）
- CI 构建由 GitHub Actions 自动触发
- 217 部署命令：
  ```bash
  cd /opt/platform
  git pull
  docker compose pull park-space
  docker compose up -d park-space
  ```

## 附录 — park-space 迁移复盘（流程改进依据）

### 9 个质量问题分布

| 阶段 | 问题数 | 典型问题 |
|------|--------|---------|
| 代码风格 | 2 | `((Number) obj)` ClassCastException、UI 卡片→表格 |
| 架构设计 | 2 | RoomPurpose/KIT parkId 错误绑定 |
| 校验缺失 | 2 | 必填字段未校验、设备去重缺失 |
| 功能缺失 | 3 | 出租出售、公共空间编辑报错、房间详情子表 tabs |

### 改进点对照

| park-space 做法 | 新流程做法 |
|----------------|-----------|
| 整模块迁移 | 页面级逐步迁移 |
| copy 同时改代码 | copy 与 adapt 分离 |
| 部署后用户发现问题 | 步骤 5 提前确认 |
| 无依赖清单 | 步骤 4 依赖树扫描 |
| 无改造清单 | 步骤 4.5 标注处理方式 |
| 无质量门禁 | 每页完成后三命令验证 |
