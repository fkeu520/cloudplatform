# 云枢中台建设中长期规划

**版本**: v1.0
**日期**: 2026-06-03
**范围**: 性能优化（L2）+ 中台能力建设（5 层）
**核心原则**: 可用性 > 可扩展性 > 性能

---

## 〇、设计原则（贯穿全篇）

| 原则 | 含义 | 反例 |
|------|------|------|
| **可用性优先** | 任何优化不得引入消息丢失、首请求延迟、扩展性下降 | 全局懒加载导致 `@KafkaListener` 启动时序错乱 |
| **不锁死技术栈** | 依赖能加能减，新人 onboarding 不困惑 | 删 pom 依赖让 IDE 失能 |
| **配置驱动 > 硬编码** | 任何开关通过配置项而非代码控制 | `spring.autoconfigure.exclude` 硬排除 |
| **可回滚性** | 每个改动必须能 1 分钟内回退 | 一次 commit 跨 5 个文件 |
| **可观测性先行** | 没有监控的优化是盲改 | "内存省了但接口慢了不知道" |

> **本原则的来源**: 2026-06-03 L2 方案 v1.0 → v2.0 修订时的反思（详见附录 B）。

## 二、L2 性能优化（v2.0 保守修订）

### 2.1 v1.0 违规审计（已废弃）

| 编号 | 原方案 | 违规 | 严重度 |
|------|------|------|------|
| V1 | 全局 `lazy-initialization=true` | 破坏 `@KafkaListener` 启动时序 | 🔴 严重 |
| V2 | 排除 `platform-workflow` 的 Flyway | Flowable auto-DDL 接管 | 🔴 严重 |
| V3 | 排除 `platform-user` 的 Flyway | 业务关键迁移 V1-V19 | 🔴 严重 |
| V4 | Phase 3 删 pom 依赖 | 技术栈锁死 | 🔴 严重 |
| V5-V8 | 硬编码排除/参数 | 扩展性受限 | 🟡 中等 |

### 2.2 v2.0 三阶段总览

| 阶段 | 改动 | 工作量 | 风险 | 收益 |
|------|------|------|------|------|
| Phase A 公共调优 | 线程池/连接池/JVM 调优 | 1 小时 | 零 | -150MB |
| Phase B 行为开关化 | `@ConditionalOnProperty` 替代硬排除 | 半天 | 低 | -70MB |
| Phase C 灰度 + 监控 | 3 批 24h 观察 + 性能基准 | 1 天 | 低 | 回归保护 |
| **合计** | - | **~2 天** | 低 | **-220MB** |

### 2.3 Phase A: 纯调优（零行为变更）

#### A.1 Tomcat 线程池（差异化）

```yaml
# 每个 application.yml 末尾追加
server:
  shutdown: graceful              # 滚动更新时优雅关闭
  tomcat:
    threads:
      max: ${TOMCAT_THREADS_MAX:80}
      min-spare: ${TOMCAT_THREADS_MIN:10}
    accept-count: 100
    max-connections: 2000
    connection-timeout: 20s

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s   # 优雅关闭超时
```

| 服务 | TOMCAT_THREADS_MAX | 依据 |
|------|------|------|
| platform-gateway | 200 | 流量汇聚点 |
| platform-auth | 100 | 登录路径必经 |
| platform-user | 80 | 普通业务 |
| platform-message | 80 | 普通业务 |
| platform-workflow | 100 | 流程审批可能瞬时并发高 |
| platform-ops | 60 | 运营后台并发低 |

#### A.2 Redis 连接池（差异化）

```yaml
spring:
  data:
    redis:
      lettuce:
        pool:
          max-active: ${REDIS_POOL_MAX:8}
          max-idle: ${REDIS_POOL_MAX:8}
          min-idle: 2
          max-wait: 2s
```

| 服务 | REDIS_POOL_MAX |
|------|------|
| platform-gateway | 20（限流）|
| platform-auth | 16（Token 高频）|
| platform-message | 12（站内信缓存）|
| platform-workflow | 12（流程变量缓存）|
| platform-user | 8 |
| platform-ops | 8 |

#### A.3 Kafka 消费参数

```yaml
spring:
  kafka:
    consumer:
      concurrency: ${KAFKA_CONSUMER_CONCURRENCY:1}  # 默认 1 副本 1, 扩容时 +1
      max-poll-records: ${KAFKA_MAX_POLL:50}
    producer:
      acks: all
      retries: 3
      properties:
        enable.idempotence: true
        max.in.flight.requests.per.connection: 1
```

#### A.4 数据库连接池（**v2.1 新增**）

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: ${DB_POOL_MAX:10}    # MySQL 默认 10, 高并发下要提到 20
      minimum-idle: 2
      connection-timeout: 20000
      max-lifetime: 1800000                   # 30min 强制重建, 防 MySQL wait_timeout
      idle-timeout: 600000
      pool-name: ${spring.application.name}-pool
```

| 服务 | DB_POOL_MAX |
|------|------|
| platform-gateway | 5（无 DB, 但 hikari 仍要配置默认值）|
| platform-auth | 5（无 DB）|
| platform-user | 20 |
| platform-message | 20 |
| platform-workflow | 30（Flowable 高频 DB 访问）|
| platform-ops | 15 |

#### A.5 响应压缩（**v2.1 新增**）

```yaml
server:
  compression:
    enabled: true
    mime-types: application/json,application/xml,text/html,text/plain
    min-response-size: 1024
```

#### A.6 异步日志（**v2.1 新增**）

`logback-spring.xml` 加 async appender 包装，避免 logstash encoder 同步阻塞：

```xml
<appender name="ASYNC_LOGSTASH" class="ch.qos.logback.classic.AsyncAppender">
  <queueSize>2048</queueSize>
  <discardingThreshold>0</discardingThreshold>
  <neverBlock>true</neverBlock>
  <appender-ref ref="LOGSTASH" />
</appender>
```

#### A.7 JVM 堆 + GC

```yaml
# docker-compose.yml
environment:
  - JAVA_OPTS=${JAVA_OPTS:--Xmx768m -Xms384m -XX:+UseG1GC -XX:MaxGCPauseMillis=100 -XX:+UseStringDeduplication -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/heapdump.hprof}
```

**差异化**（生产 8C16G）：

| 服务 | -Xmx | -Xms |
|------|------|------|
| platform-gateway | 512m | 256m |
| platform-auth | 512m | 256m |
| platform-user | 768m | 384m |
| platform-message | 768m | 384m |
| platform-workflow | 1024m | 512m |
| platform-ops | 768m | 384m |

> **关于 GC**: G1GC 在 1GB 堆以下表现良好。workflow 堆 1GB 时如出现 P99 > 100ms，可换 ZGC（`-XX:+UseZGC`）。

#### A.8 预期收益

| 项 | 节省 | 原因 |
|------|------|------|
| Tomcat 线程栈 | -100MB | 200 → 80 |
| Redis 连接池 | -50MB | 默认无界 → 显式限制 |
| 响应压缩 | 0（CPU 换带宽）| 节省 60-80% 网络流量 |
| **合计** | **-150MB + 网络优化** | **零行为变更** |

### 2.4 Phase B: 行为开关化（@ConditionalOnProperty）

> **核心**: 不是"禁用能力"，而是"按需启用能力"。

#### B.1 开关配置（Nacos `common.yml`）

```yaml
platform:
  features:
    mail-enabled: ${PLATFORM_MAIL_ENABLED:false}
    kafka-producer-enabled: ${PLATFORM_KAFKA_PRODUCER_ENABLED:true}
    feign-enabled: ${PLATFORM_FEIGN_ENABLED:true}
```

> **重要**: 开关从**本地 application.yml 读 env var** 而非 Nacos 热加载。原因是 `@ConditionalOnProperty` 在 Spring 启动期评估，Nacos 配置此时尚未注入。

#### B.2 各服务开关化

| 服务 | 开关 | 节省 | 必要性 |
|------|------|------|------|
| platform-message | mail-enabled=false | -30MB | 🟡 |
| platform-user | kafka-producer-enabled=false | -20MB | 🟢 |
| platform-ops | kafka-producer-enabled=false | -20MB | 🟢 |
| platform-auth | feign-enabled=false | -50MB | ❌ 跳过（强依赖）|

#### B.3 实施模式

```java
// 新增 MailConfig.java
@Configuration
@ConditionalOnProperty(name = "platform.features.mail-enabled", havingValue = "true", matchIfMissing = false)
public class MailConfig {
    @Bean
    public JavaMailSender mailSender() { ... }
}

// 调用方改造
@Autowired(required = false)  // 加 required=false, 关闭时不抛
private JavaMailSender mailSender;
```

> **回滚**: Nacos 改 `true` → 30s 内下次启动生效（改 env var 即可）。

### 2.5 Phase C: 灰度 + 监控保障

#### C.1 灰度策略

```
批次 1: platform-user
  24h 观察 → 指标正常 → 进入批次 2
  
批次 2: platform-gateway + platform-auth
  24h 观察 → 网关 RT/登录成功率正常 → 批次 3

批次 3: platform-message + platform-workflow + platform-ops
  24h 观察 → 消息发送成功率/流程审批成功率正常 → 全量完成

总周期: 3 天 + 周末观察 1 天
```

> **跨周末**: 周一到周三发版，周三到周日完整工作日负载验证。

#### C.2 监控指标

写入 [`性能基准.md`](性能基准.md)：

| 指标 | 工具 | 阈值 |
|------|------|------|
| 容器内存 | docker stats | < Xmx × 1.3 |
| 堆使用率 | `/actuator/metrics/jvm.memory.used` | < 80% |
| GC 暂停 | `/actuator/metrics/jvm.gc.pause` P99 | < 100ms |
| 接口 RT | Micrometer Timer | P99 < 500ms |
| Kafka 消费 lag | Kafka Admin API | < 100 |
| HikariCP 活跃连接 | `/actuator/metrics/hikaricp.connections.active` | < max-pool × 0.8 |

### 2.7 容量规划

> **算账再优化**: 基于业务假设算清，再决定优化幅度。

#### 业务假设（2026 H2 预期）

| 指标 | 值 |
|------|------|
| 日活用户 | 5,000 |
| 峰值并发 | 500（早上 9-10 点）|
| 平均每人每日请求 | 200 |
| 峰值 QPS | 1,000 |
| 工作流日发起量 | 1,000 |
| 消息日发送量 | 50,000 |

#### 资源计算公式

```
Tomcat 线程数:
  每请求 200ms → 单线程 QPS = 5
  200 QPS/service / 5 = 40 线程
  × 1.5 缓冲 = 60
  × 2 副本分摊 = 30/pod

Redis 连接数:
  500 并发 × 10% 同时访问 Redis = 50
  ÷ 6 服务 ÷ 2 副本 = 4/pod
  推荐 8 (含缓冲)

DB 连接数 (HikariCP):
  200 QPS × 50ms 平均查询 = 10 活跃连接
  × 1.5 缓冲 = 15
  ÷ 2 副本 = 8/pod
  推荐 15-20
```

#### 容量结论

**8C16G 单机 + 双副本可承载 500 峰值并发**, 足够到 2027 H1。

## 四、中台能力建设 5 层蓝图

> **核心**: 性能优化是省钱，能力建设是**避免出事**+**释放价值**。

### 4.1 🔴 P0 - 中台核心特性（必须做）

| 项 | 现状 | 风险/缺口 | 优先级 |
|------|------|------|------|
| **多租户隔离** | DB 有 `tenant_id` 字段 | **缺拦截器**：任何查询忘加条件即越权 | P0-1 |
| **数据权限 (data_scope)** | RBAC 菜单权限有 | **缺行级数据范围**（"只能看本部门"）| P0-2 |
| **统一认证 / SSO** | JWT 单应用 | **缺 OAuth2/OIDC Provider** | P0-3 |
| **业务能力地图** | 微服务拆分清晰 | **缺能力目录**（API 文档聚合 + 业务分类）| P0-4 |

### 4.2 🟠 P1 - 可观测性（多服务必备）

| 项 | 现状 | 风险/缺口 | 优先级 |
|------|------|------|------|
| **链路追踪** | 无 Sleuth/Zipkin | 跨服务调用出问题**无法定位慢请求** | P1-1 |
| **统一错误码** | 散落各 Result 类 | 前端展示依赖字符串 | P1-2 |
| **业务监控大盘** | 有 ELK（日志）| 缺业务指标（活跃用户、流程审批时长）| P1-3 |
| **告警分级** | 无 | 缺 P0/P1/P2 分级，故障时全员 oncall | P1-4 |
| **业务指标采集** | 无 | 缺 Micrometer + Prometheus | P1-5（**新增**）|

#### P1-5 业务指标体系（Micrometer + Prometheus）

**当前缺口**:
- 只有基础设施指标（docker stats、JVM GC）
- 缺业务健康度：流程审批 P99、消息触达率、租户活跃度
- 事故时无法回答"影响多少用户"

**指标清单**:

| 类别 | 指标名 | 类型 | 用途 |
|---|---|---|---|
| **业务 Counter** | `workflow_started_total{process=...}` | Counter | 流程发起量 |
| | `task_completed_total{process=..., outcome=approved/rejected}` | Counter | 任务完成分布 |
| | `message_sent_total{channel=..., status=success/failed}` | Counter | 消息触达率 |
| | `user_login_total{tenant=...}` | Counter | 活跃租户 |
| | `api_call_total{service=..., endpoint=..., status=2xx/4xx/5xx}` | Counter | API SLA |
| **业务 Timer** | `workflow_approval_duration_seconds` | Timer | 审批 P50/P95/P99 |
| | `login_duration_seconds` | Timer | 登录耗时 |
| | `db_query_duration_seconds{table=...}` | Timer | 慢查询 |
| **业务 Gauge** | `tenant_count_active` | Gauge | 当前活跃租户 |
| | `kafka_consumer_lag{topic=..., group=...}` | Gauge | 消费积压 |
| | `redis_connection_pool_active` | Gauge | Redis 连接数 |

**展示与告警**:
- Grafana 大盘: 业务指标 + 基础设施指标
- 告警分级: P0（5xx > 1%）→ 立即呼叫；P1（审批 P99 > 30s）→ Slack；P2（消息失败率 > 5%）→ 邮件

**实施位置**: 每个 platform-* 服务加 `micrometer-registry-prometheus` 依赖 + `@Counted/@Timed` 注解。

**优先级**: M6 与 P1-1 链路追踪一并实施。

### 4.3 🟡 P2 - 开放性（决定中台能否被集成）

| 项 | 现状 | 风险/缺口 | 优先级 |
|------|------|------|------|
| **API 文档聚合** | 各服务独立 Knife4j | 缺统一门户 | P2-1 |
| **API 版本管理** | 无 URL 前缀 | 缺 `/api/v{version}/` 规范 | P2-2 |
| **API 配额/限流** | gateway 粗粒度 | 缺租户/IP/接口三维限流 | P2-3 |
| **SDK 客户端** | 无 | 缺 Java/Python/Node SDK | P2-4 |
| **Webhook 回调** | Kafka 内部 | 缺对外 Webhook 通知 | P2-5 |
| **前端组件库** `@cloudhub/components` | 平台两 admin 重复封装 | 抽取共享组件 | P2-6 |
| **前端微前端** | 单体 Vue 3 | 3+ 业务线时再考虑 | P2-7（Q1 2027 评估）|

#### P2-6 前端中台化：分阶段实施

**当前状态**: 两个 admin 前端，重复封装 Element Plus 组件。

**采纳方案**:

| 阶段 | 内容 | 工作量 | 触发 |
|---|---|---|---|
| **A. 组件库抽取** | `@cloudhub/components` (Element Plus 业务封装) | 1 周 | ✅ 立即 |
| **B. 工具库抽取** | `@cloudhub/utils` (request/formatters/validators) | 3 天 | ✅ 立即 |
| **C. 微前端** | Module Federation / qiankun | 2 周 | 3+ 业务前端时 |

**不立即做微前端的理由**:
- 学习成本和构建复杂度高
- 当前只有 2 个 admin，重复代码量可控
- 团队边界尚未出现冲突

**P2-7 微前端触发条件**:
- 独立业务前端 ≥ 3 个
- 出现团队间 PR 冲突 ≥ 5/周
- 单一应用构建时间 > 5 分钟

### 4.4 🟢 P3 - 韧性 / 灾备（生产必备）

| 项 | 现状 | 风险/缺口 | 优先级 |
|------|------|------|------|
| **数据库备份演练** | 策略文档有 | 缺定期演练 | P3-1 |
| **灰度发布** | 无 | 缺流量染色/Feature Flag | P3-2 |
| **降级策略** | 无 | 缺核心链路降级开关 | P3-3 |
| **混沌工程** | 无 | 故障演练靠运气 | P3-4 |
| **异地多活** | 单机房 | 后期会卡这个点 | P3-5 |
| **API 网关韧性** | 仅路由 + 粗粒度限流 | 缺细粒度熔断/重试/超时 | P3-6（**提升优先级**）|
| **分布式事务** | 仅 Kafka 异步 | 缺事务消息/Outbox 模式 | P3-7（**采纳中优先级**）|

#### P3-6 API 网关韧性设计

| 能力 | 实现 | 风险 |
|---|---|---|
| **细粒度熔断** | Resilience4j `@CircuitBreaker`（按 downstream 维度）| 低 |
| **细粒度重试** | `Retry` filter（带指数退避，仅幂等接口）| 低 |
| **滑动窗口限流** | Redis Lua（精确到秒级）| 低 |
| **全链路超时** | `httpclient.response-timeout` + Sentinel | 中 |
| **灰度路由** | Nacos 权重 + RoutePredicate | 中 |
| **API 配额** | Redis 计数器 + 租户/接口二维 | 中 |

**优先级调整原因**: 网关是唯一流量入口，缺韧性 = 全局风险。从 P3 韧性内部**最优先**实施（M6 启动时）。

#### P3-7 分布式事务 / 最终一致性

**当前风险场景**:
- workflow 审批通过 → 消息发送失败（Kafka 消费者宕机）→ 用户收不到通知
- 租户创建 → 下游 user/auth/ops 初始化失败 → 新租户无法登录
- 流程发起 → 候选人查找失败 → 任务未分配

**采纳方案**: 本地消息表 + Outbox 模式（不引入 Seata）

```
核心思路:
  1. 业务 DB 同事务写 outbox 表 (status=pending, payload=...)
  2. 定时任务扫描 pending -> 投到 Kafka
  3. 消费端手动 ack + 失败按指数退避重试
  4. N 次失败入死信表 + 告警

为什么不用 Seata/TCC:
  - TCC 复杂度高, 业务侵入大
  - Saga 流程定义复杂, Flowable 已覆盖部分
  - 2PC 阻塞严重, 中台场景不适合
  - Outbox 是 90% 场景的最优解

实施位置:
  - platform-common: OutboxMessage 实体 + 定时任务
  - workflow: 审批通过时同事务写 outbox
  - message: Outbox 消费, 投递到渠道
```

**优先级**: M5 完成后启动（M6 末或 M7 初）。

### 5.1 P0-1 MyBatis-Plus 多租户拦截器（2 天）

**目标**: 所有 SQL 自动加 `WHERE tenant_id = ?`，**一处遗漏即越权**。

#### 5.1.1 现状审计

| 现状 | 风险 |
|------|------|
| DB 表有 `tenant_id` 列 | 列存在但**没有任何代码强制使用** |
| sys_user.tenantId 字段存在 | 业务代码 `UserMapper.selectList()` 不会自动加 |
| `LoginUser.tenantId` 存在 | 但 ThreadLocal 没存当前租户 |

#### 5.1.2 实施方案

**Step 1: TenantContext (ThreadLocal)**

```java
// 新增 platform-common/tenant/TenantContext.java
public class TenantContext {
    private static final ThreadLocal<Long> CURRENT = new ThreadLocal<>();
    public static void set(Long tenantId) { CURRENT.set(tenantId); }
    public static Long get() { return CURRENT.get(); }
    public static void clear() { CURRENT.remove(); }
}
```

**Step 2: TenantInterceptor (Web)**

```java
// 新增 platform-common/web/TenantInterceptor.java
@Component
public class TenantInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(...) {
        String tenantId = request.getHeader("X-Tenant-Id");
        if (tenantId == null) {
            // JWT 优先
            tenantId = JwtUtil.getTenantId(request);
        }
        if (tenantId == null) throw new BizException("缺少租户标识");
        TenantContext.set(Long.parseLong(tenantId));
        return true;
    }
    @Override
    public void afterCompletion(...) { TenantContext.clear(); }
}
```

**Step 3: MyBatis-Plus TenantLineInnerInterceptor**

```java
// 新增 platform-common/mybatis/MybatisPlusConfig.java
@Configuration
public class MybatisPlusConfig {
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        TenantLineInnerInterceptor tenant = new TenantLineInnerInterceptor(new TenantLineHandler() {
            @Override
            public Expression getTenantId() {
                return new LongValue(TenantContext.get());
            }
            @Override
            public boolean ignoreTable(String tableName) {
                // sys_dict / sys_config 等系统表不加
                return IGNORE_TABLES.contains(tableName);
            }
        });
        interceptor.addInnerInterceptor(tenant);
        return interceptor;
    }
}
```

**Step 4: 注册 Web 拦截器**

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Autowired private TenantInterceptor tenantInterceptor;
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(tenantInterceptor)
            .addPathPatterns("/**")
            .excludePathPatterns("/auth/login", "/auth/captcha", "/error");
    }
}
```

#### 5.1.3 验证清单

- [ ] 单元测试: `UserMapper.selectList()` 生成的 SQL 包含 `tenant_id = ?`
- [ ] 集成测试: 两个租户登录后互不可见
- [ ] CI 加 check: `grep -rn "selectList\|selectByMap" code/ --include="*.java"` 人工 review 确认无遗漏
- [ ] SQL 审计脚本: 扫描 `tenant_id IS NULL` 的生产表

#### 5.1.4 风险与回滚

| 风险 | 缓解 |
|------|------|
| 系统表误加租户条件 | `ignoreTable` 显式列出 sys_dict 等 |
| 旧数据无 tenant_id | 上线前 backfill（`UPDATE table SET tenant_id = 1 WHERE tenant_id IS NULL`）|
| 拦截器漏注册 | 启动期自检: `SELECT 1 FROM sys_user WHERE tenant_id = 9999`（9999 租户不应有数据）|

### 5.2 P0-2 数据权限 data_scope（1 周）

**目标**: 同角色不同数据范围（如"销售"角色，经理看本部门，员工看本人）。

#### 5.2.1 现状

| 现状 | 风险 |
|------|------|
| `sys_role` 表有 | 缺 `data_scope` 字段 |
| `sys_user.dept_id` 有 | 缺 dept 子树查询 |
| 业务查询 `userMapper.selectList()` | 不带任何数据范围条件 |

#### 5.2.2 实施方案

**Step 1: sys_role 加字段**

```sql
-- V20__add_data_scope.sql
ALTER TABLE sys_role ADD COLUMN data_scope TINYINT DEFAULT 1
  COMMENT '1=全部 2=本部门 3=本部门及下级 4=本人 5=自定义';
ALTER TABLE sys_role ADD COLUMN custom_dept_ids VARCHAR(1000) DEFAULT NULL
  COMMENT '自定义部门ID列表 (data_scope=5)';
```

**Step 2: DataScopeAspect (AOP)**

```java
@Aspect
@Component
public class DataScopeAspect {
    @Before("@annotation(dataScope)")
    public void apply(JoinPoint jp, DataScope dataScope) {
        // 1. 从 ThreadLocal 取当前 userId, role
        // 2. 查 role.data_scope
        // 3. 根据 data_scope 拼 SQL 条件:
        //    1=全部 → 不加条件
        //    2=本部门 → WHERE dept_id = ?
        //    3=本部门及下级 → WHERE dept_id IN (子部门)
        //    4=本人 → WHERE user_id = ?
        //    5=自定义 → WHERE dept_id IN (custom_dept_ids)
        // 4. 用 ThreadLocal 传给 MyBatis 拦截器
    }
}
```

## 八、附录 B: 思考过程记录

> **记录目的**: 避免下次重新走弯路。沉淀 "为什么这样决策"。

### B.1 为什么先做多租户拦截器而不是 SSO

| 因素 | 多租户拦截器 | SSO |
|------|------|------|
| 风险紧迫度 | 🔴 一次越权就是 P0 事故 | 🟠 影响接入体验, 不直接出事 |
| 实施前置 | 无 | 需先有"被接入方" |
| 投资回报 | 防事故, ROI 极高 | 提升易用性, ROI 中等 |
| 顺序 | ✅ **先做** | ❌ 后做 |

### B.2 为什么 L2 性能优化放在 P0-1 之后

| 阶段 | 收益 | 风险 |
|------|------|------|
| 先做 L2 性能优化 | 省 200MB 内存 | 优化上线后才发现 P0-1 多租户拦截器, 返工 |
| 先做 P0-1 多租户拦截器 | 防越权事故 | 拦截器上线可能影响性能, 需 L2 重新调优 |
| **推荐顺序** | P0-1 → P0-2 → P1-1 → L2 | 安全性优先, 优化服务于安全 |

### B.3 为什么"v1.0 → v2.0"是必要的

v1.0 看起来"省得多"，但实际：

| 表面 | 实际 |
|------|------|
| -1.0GB 内存 | 真实可获得 -300MB（多数排除项违规）|
| 零业务影响 | 全局懒加载破坏消息可靠性 |
| 可扩展 | 删除依赖让新人困惑 3 个月 |
| 1.5 周工作量 | 实际 4 周（含返工）|

**教训**: 优化方案的"承诺收益" 经常被高估 2-3 倍, "风险" 经常被低估 2-3 倍。两者相乘就是项目延期/事故的根因。

### B.4 中台 5 层建设的优先级逻辑

```
为什么 P0 > P1 > P2 > P3 > P4?

P0 (核心): 不做, 平台不是"中台", 只是"微服务集群"
P1 (可观测): 不做, 上生产后无法运维, 必然烂掉
P2 (开放): 不做, 中台价值 = 0, 没人接入
P3 (韧性): 不做, 一次故障全盘崩溃
P4 (业务): 不做, 长期价值受限, 但短期可活
```

### B.5 为什么不推荐 Modular Monolith (L3-A)

v2.0 之前提过 L3-A 合并 6 服务为单应用。**重新评估后不推荐**：

| 反对理由 | 说明 |
|------|------|
| 失去独立扩缩容 | workflow 流量是 user 的 5 倍, 合并后只能同步扩 |
| 失去故障隔离 | user 内存泄漏会拖垮 workflow |
| 失去团队边界 | 6 个团队合 1 个 PR 队列 |
| 节省 2.8GB 内存 | 在 8C16G 双副本场景下价值有限 |

**只在以下情况考虑合并**:
- 6 服务中 < 3 人在维护
- 内存资源极度紧张 (4C8G 单机)
- 业务高度耦合（如订单 + 支付 + 库存）

### B.6 微服务粒度判据（不重组但记录）

**当前 6 服务粒度评估**:

| 服务 | 评价 | 建议 |
|---|---|---|
| platform-user | 核心域 | 保留 |
| platform-auth | 略细（与 user 合并可考虑）| 视团队规模 |
| platform-message | 独立业务域 | 保留 |
| platform-workflow | 重引擎 | 必须独立 |
| platform-gateway | 必须独立 | 保留 |
| platform-ops | 略细（与 user 合并可考虑）| 视团队规模 |

**合并判据**（满足任一即建议合并）:

| 条件 | 当前值 | 触发 |
|---|---|---|
| 单团队 < 5 人维护 3+ 服务 | 6+ 人 | 暂不 |
| 内存资源极度紧张 (4C8G) | 8C16G | 暂不 |
| 服务间调用 > 80% 流量 | < 50% | 暂不 |
| 团队明确同意承担合并后 PR 拥堵 | — | 暂不 |

**拆分判据**（满足任一即建议拆分）:
