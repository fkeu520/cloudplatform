## 二、合理性分析

### ✅ 优点

| 方面 | 说明 |
|------|------|
| **版本管理规范** | 文档标注版本(v1.0/v7.0)、废弃状态明确，历史版本有backup目录 |
| **角色分工清晰** | 主规划(中长期规划) vs 实施历史(opencode实施计划) vs 变更日志(项目进度) 各有侧重 |
| **专项隔离** | P0-1/M5等专项有独立文档，避免主规划过度膨胀 |
| **问题追踪集中** | KNOWN_ISSUES.md统一记录，按状态(🔴🟡🟢)分类，当日闭环 |
| **决策记录留存** | 决策记录文档化，包含3选1方案对比+理由+风险 |
| **交接文档** | HANDOFF文档用于跨会话接续，已废弃的旧版有明确DEPRECATED标记 |

### ⚠️ 问题

| 问题 | 说明 | 影响 |
|------|------|------|
| **1. 文档数量过多(30+)** | 同类型文档分散，如"实施计划"类有3个文档 | 查找困难，易重复 |
| **2. 项目进度.md过度膨胀** | 63KB，包含从M4到v7.3的全部变更，既是历史又是规划 | 难以快速定位 |
| **3. 废弃文档未清理** | Phase1-实施计划/蓝图框架/0604-handoff仍保留，有backup_20260528 | 冗余文件 |
| **4. 编码规范分散** | Java/前端/数据库3个独立文件，无统一入口 | 新成员需自己找 |
| **5. 技术方案 vs 实施计划 vs 进度交叉** | 三者都描述同一内容的不同侧面，更新时易遗漏 | 信息不一致 |
| **6. 缺乏索引/导航** | 没有doc/README.md作为总入口 | 找不到文档 |
| **7. 配置类文档分散** | 部署/环境/服务器配置/API规范分散在5个文件 | 部署时翻多个文件 |
| **8. 决策记录与实施子任务分离** | M5决策记录和实施子任务是两个文档，实际需对照阅读 | 阅读成本高 |

## 三、文档合并建议

### 方案A：最小合并（推荐，先降低数量）


### 方案B：分层归档（推荐，按生命周期）

```
doc/
├── README.md                             ← 文档索引
├── plan/                                 ← 规划类(低频变更)
│   ├── 中台建设中长期规划.md              (主规划)
│   ├── 技术方案.md                        (实施技术细节)
│   └── 视觉与交互规范.md
├── log/                                  ← 日志类(高频追加)
│   ├── 项目进度.md                        (变更日志，每周追加)
│   └── KNOWN_ISSUES.md                    (问题追踪，每日更新)
├── spec/                                 ← 规范类(变更中等)
│   ├── 编码规范.md                        (Java+前端+数据库)
│   └── API接口规范.md
├── ops/                                  ← 操作类(部署时看)
│   ├── 部署指南.md
│   ├── 环境搭建指引.md
│   ├── CI_CD操作手册.md
│   ├── 数据库备份策略.md
│   └── git-workflow.md
├── decision/                             ← 决策记录(归档)
│   ├── P0-1多租户决策.md                  (合并3个P0-1文档)
│   └── M5数据权限决策.md                  (合并3个M5文档)
├── handoff/                              ← 交接(过期归档)
│   └── 2026-06-05.md
├── scripts/                              ← SQL脚本
│   ├── mysql-schema.sql
│   └── pr1-cte-verification.sql
└── backup/                               ← 历史归档
    └── 20260528/                          (旧版备份)
        └── ...
```

**按目录分层的优势：**
- 规划类文档(plan/)：变更频率低，长期稳定
- 日志类文档(log/)：高频追加，独立目录避免污染
- 操作类文档(ops/)：部署时集中查看，无需翻多个目录
- 决策记录(decision/)：归档性质，决策一旦拍板不再修改

## 六、总结

| 维度 | 当前 | 建议 | 工作量 |
|------|------|------|--------|
| 文档数量 | 30+ | 11-12个主文件 | 2小时整理 |
| 目录结构 | 全部扁平 | 按生命周期分层 | 1小时创建 |
| 总入口 | 无 | doc/README.md | 30分钟 |
| 废弃清理 | 3个废弃+backup目录 | 统一归档到backup/ | 30分钟 |
| 项目进度.md | 63KB一次性看完 | 拆分历史归档，主文件只留2周 | 1小时 |

**推荐优先做：创建 README.md + 按目录分层 + 合并编码规范**，这是性价比最高的改动。
