## 一、问题陈述

**当前现状** (`MybatisPlusConfig.java:36-54`):

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(...));
    interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
    return interceptor;
}
```

- 拦截器**始终加载**，无法运行时关闭
- IGNORE_TABLES 19 个表名**硬编码**在 `:24-33`
- 紧急情况（如发现某 SQL 漏租户条件导致越权）**无法秒级回滚**，只能发版

**用户偏好**（来自 handoff + 主规划）:
- **可回滚**（"先分析合理性 + 给出决策 + 解释理由"）
- **谨慎**（不可用性 > 可扩展性 > 性能）
- 文档先行

**目标**: 设计**运行时回滚开关**，紧急情况可秒级关闭拦截器（=回到 P0-1 之前行为）。

---

## 二、设计原则

| 原则 | 含义 |
|------|------|
| **可用性 > 一切** | 拦截器导致业务异常时，能立即关闭，不需发版 |
| **启动期评估** | 开关在 Spring 启动期读取，**不接受运行时热变更**（避免半启动状态行为漂移） |
| **环境变量优先** | 开关值从环境变量读，**Nacos 改动只作为可视化参考**（不参与实际配置） |
| **默认开启** | 开关缺失 = 拦截器加载 = 当前行为，**新装环境立刻安全** |

## 三、3 个方案对比

### 方案 A: `@ConditionalOnProperty` 整体开关（推荐）

**核心**: 用 Spring `@ConditionalOnProperty` 控制 `MybatisPlusConfig` 整个 `@Bean` 方法的创建。

**改动**:

```java
@Configuration
@ConditionalOnProperty(name = "platform.tenant.interceptor.enabled", havingValue = "true", matchIfMissing = true)
public class MybatisPlusConfig implements MetaObjectHandler {

    private static final Set<String> IGNORE_TABLES = Set.of(...);

    @Bean
    @ConditionalOnProperty(name = "platform.tenant.interceptor.enabled", havingValue = "true", matchIfMissing = true)
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        // ... 同现状
    }

    // 关闭时的占位 Bean（保证其他依赖 MybatisPlusInterceptor 的代码不崩溃）
    @Bean
    @ConditionalOnProperty(name = "platform.tenant.interceptor.enabled", havingValue = "false")
    public MybatisPlusInterceptor mybatisPlusInterceptorDisabled() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
        return interceptor;
    }

    // ... 其他 Bean（identifierGenerator, insertFill, updateFill）保留
}
```

**配置** (`application.yml` + `bootstrap.yml` 各自注入):

```yaml
platform:
  tenant:
    interceptor:
      enabled: ${PLATFORM_TENANT_INTERCEPTOR_ENABLED:true}
```

**回滚操作**:

```bash
# 紧急回滚: 在出问题的服务容器里设环境变量
docker compose up -d \
    -e PLATFORM_TENANT_INTERCEPTOR_ENABLED=false \
    platform-user
# 30s 内拦截器不加载, 业务回到 v3.1 行为
```

**优点**:
- 改动小（~15 行）
- 与 Spring 启动期评估时机一致，**行为可预测**
- 不引入 `@RefreshScope`，避免热加载陷阱
- 关闭时仍保留 `PaginationInnerInterceptor`，**业务代码不报错**

**缺点**:
- 新增表时**仍需改代码 + 发版**（仅是"加表"需求）
- 关闭后**真的没拦截**（与主规划"9999 租户"自检思路不一致）

---

### 方案 B: Nacos `@RefreshScope` 动态改 IGNORE_TABLES

**核心**: 把 19 个 IGNORE_TABLES 改成 `@Value("${platform.tenant.ignore-tables}")` + `@RefreshScope`，运行时改 Nacos 配置后 Spring 重建 Bean。

**改动**:

```java
@RefreshScope
@Configuration
public class MybatisPlusConfig implements MetaObjectHandler {

    @Value("${platform.tenant.ignore-tables:flyway_schema_history,sys_tenant,...}")
    private List<String> ignoreTables;

    @Bean
    @RefreshScope
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        // 用 ignoreTables 替代硬编码
    }
}
```

**配置** (Nacos `common.yml`):

```yaml
platform:
  tenant:
    ignore-tables: flyway_schema_history,sys_tenant,sys_message,...
```

**回滚操作**:

```bash
# Nacos 控制台加配置 platform.tenant.ignore-tables=*
# 或 platform.tenant.interceptor.enabled=false
# 30s 内 @RefreshScope 重建 Bean
```

**优点**:
- 真正"运行时变更"，**不需要重启**
- 紧急加表（不在 IGNORE_TABLES 里）可秒级补

**缺点**:
- **引入 `@RefreshScope`**，行为不可预测（已记录 L6 v2.1 待复查）
- 半启动状态: 拦截器在重建过程中，**可能执行 N 次无拦截 SQL**
- 与项目 L2 优化"不引入 RefreshScope"原则**冲突**
- 调试困难：开发环境无法确定当前生效的 IGNORE_TABLES

---

### 方案 C: 双写（同时支持 A 和 B）

**核心**: 拦截器默认加载，**同时**提供环境变量开关 + Nacos 开关。

**缺点**:
- 维护成本 ×2
- 行为可能漂移（env var 和 Nacos 哪个优先？）
- 复杂度爆炸

**不推荐**。

## 四、方案对比矩阵

| 维度 | A: ConditionalOnProperty（推荐）| B: Nacos RefreshScope | C: 双写 |
|------|------------------------------|---------------------|--------|
| 改动量 | 小（~15 行）| 中（~30 行 + 配置）| 大 |
| 启动期一致性 | ✅ 完全一致 | ⚠️ 半启动期可能漏拦截 | ⚠️ 同 B |
| 行为可预测 | ✅ 高 | ❌ 低 | ❌ 低 |
| 紧急回滚时间 | ~30s（重启）| ~30s（无需重启）| ~30s |
| 新增表灵活度 | ❌ 需发版 | ✅ 改 Nacos | ✅ |
| 与 L2 优化一致性 | ✅ | ❌ | ❌ |
| 调试难度 | ✅ 低 | ⚠️ 中 | ❌ 高 |
| 推荐度 | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐ |

## 五、推荐方案 A 的实施细节

### 5.1 配置文件改动

#### 5.1.1 `application.yml` 各服务（5 个）

`platform-user / platform-auth / platform-gateway / platform-workflow / platform-message / platform-ops` 各自的 `application.yml` 末尾追加:

```yaml
platform:
  tenant:
    interceptor:
      enabled: ${PLATFORM_TENANT_INTERCEPTOR_ENABLED:true}
```

#### 5.1.2 `docker-compose.yml` 各服务（默认开启）

**不修改**——默认 `true`，所有服务按现状运行。**仅在紧急回滚时**才在受影响服务的 `environment` 块追加:

```yaml
platform-user:
  environment:
    - PLATFORM_TENANT_INTERCEPTOR_ENABLED=false  # 仅紧急情况
```

### 5.2 代码改动

#### 5.2.1 `MybatisPlusConfig.java`

- 在类上追加 `@ConditionalOnProperty`
- 拆分 `mybatisPlusInterceptor` Bean 为两个版本（启用 / 禁用）
- 保留 `identifierGenerator / insertFill / updateFill` Bean 不变

#### 5.2.2 `TenantFilter.java`

**保持不变**。TenantFilter 仅从 JWT 解析租户写入 ThreadLocal，**与拦截器是否启用解耦**。即使拦截器关闭，TenantFilter 仍正常执行（只是 SQL 不再被过滤）。

### 5.3 验证脚本

新增 `scripts/ci/check-tenant-interceptor-toggle.sh`（集成到 CI）:

```bash
#!/bin/bash
# 验证两个 Bean 互斥存在
set -e

# 启动应用 (默认 enabled=true), 验证 Bean 存在
mvn spring-boot:run -Dspring-boot.run.arguments="--platform.tenant.interceptor.enabled=true" &
PID=$!
sleep 30

# 检查 Bean
BEAN=$(curl -s http://localhost:8081/actuator/beans 2>/dev/null | \
    jq '.contexts.application.beans."mybatisPlusInterceptor"' || echo "NOT_FOUND")

if [ "$BEAN" != "NOT_FOUND" ]; then
    echo "✅ enabled=true 时 Bean 存在"
else
    echo "❌ enabled=true 时 Bean 不存在 (异常)"
    exit 1
fi

kill $PID

# 启动应用 (enabled=false), 验证 Bean 不存在
mvn spring-boot:run -Dspring-boot.run.arguments="--platform.tenant.interceptor.enabled=false" &
PID=$!
sleep 30

BEAN=$(curl -s http://localhost:8081/actuator/beans 2>/dev/null | \
    jq '.contexts.application.beans."mybatisPlusInterceptorDisabled"' || echo "NOT_FOUND")

if [ "$BEAN" != "NOT_FOUND" ]; then
    echo "✅ enabled=false 时 Disabled Bean 存在"
else
    echo "❌ enabled=false 时 Disabled Bean 不存在 (异常)"
    exit 1
fi

kill $PID
echo "✅ 开关验证通过"
```

## 六、回滚演练

### 6.1 场景 1: 单服务异常

**情境**: `platform-user` 报越权 SQL（漏加 tenant_id 条件，业务侧紧急止血）

**操作**:

```bash
# 1. 紧急回滚: 关闭 user 服务的拦截器
docker compose up -d \
    -e PLATFORM_TENANT_INTERCEPTOR_ENABLED=false \
    platform-user

# 2. 验证: 业务可恢复 (回到 v3.1 行为, 跨租户数据可见, 但不再越权丢失)
curl -H "Authorization: Bearer <user_t1_token>" http://localhost:8081/user/v3/api-docs

# 3. 修复代码后, 改回 true
docker compose up -d \
    -e PLATFORM_TENANT_INTERCEPTOR_ENABLED=true \
    platform-user
```

**耗时**: ~30s（重启） + ~10s（验证） = **1 分钟内止血**

### 6.2 场景 2: 全服务异常（极少）

**情境**: 拦截器有 BUG，导致所有 SQL 报错（如某版本 MyBatis-Plus 兼容性）

**操作**:

```bash
# 一键关闭所有后端服务
docker compose up -d \
    -e PLATFORM_TENANT_INTERCEPTOR_ENABLED=false \
    platform-user platform-auth platform-gateway platform-workflow platform-message platform-ops
```

### 6.3 场景 3: 永久关闭（绝不应发生）

**情境**: 决定彻底弃用拦截器，依赖业务层手动加 tenant_id（极差设计，**不应执行**）

**操作**: 改 `application.yml` 默认值为 `false`，重新发版。

**决策记录**: 应在主规划 v2.0 中正式增补"为何不采用业务层手动"小节，避免后人走回头路。

| 主规划描述 | 本设计 | 评价 |
|-----------|--------|------|
| 系统表误加租户条件: `ignoreTable` 显式列出 sys_dict 等 | ✅ IGNORE_TABLES 保留 19 个 | 不变 |

## 八、决策日志

### 8.1 为什么选 A 不选 B？

| 因素 | 权重 | A 评分 | B 评分 |
|------|------|--------|--------|
| 启动期行为一致性 | 高 | ✅ 高 | ❌ 低 |
| 与 L2 优化一致性 | 中 | ✅ 一致 | ❌ 冲突（L6 待复查项）|
| 紧急回滚时间 | 中 | ~30s | ~30s（**无显著优势**）|
| 维护成本 | 中 | 低 | 中 |
| 实施工作量 | 低 | ~15 行 | ~30 行 + 配置 |
| **加权总分** | - | **⭐⭐⭐⭐⭐** | ⭐⭐ |

**结论**: B 的"无需重启"优势在 ~30s 级别**不显著**，A 在可预测性 + 一致性上**显著优于** B。

### 8.2 为什么开关默认值是 true 而非 false？

- `matchIfMissing = true`: 开关缺失时 = 拦截器加载 = 当前行为
- 理由: **新装环境立刻安全**（不依赖运维记得开）
- 反例: 若默认 false，新装环境会**无任何拦截**，直到运维记得配

### 8.3 为什么 IGNORE_TABLES 不变？

- 当前 19 个表的分类（业务/平台/审计）经过审慎设计
- 改为 Nacos 动态可读是**过度工程**
- **应急方式**: 改 IGNORE_TABLES 本身应**改代码 + 发版**（强约束，避免误改）

### 8.4 与 L2 §2.4 行为开关化的关系？

| L2 §2.4 描述 | 本设计 | 关系 |
|------------|--------|------|
| `platform.features.mail-enabled` 开关 | `platform.tenant.interceptor.enabled` 开关 | ✅ **同一模式**（L2 已确立） |
| Nacos 配置 + 环境变量双写 | 仅环境变量（启动期评估） | 🟡 **简化为单写**（拦截器开关不需要 Nacos）|
| 改 env var 30s 内下次启动生效 | 同 | ✅ 一致 |
