### 2.1 ThreadLocal 上下文（`TenantContextHolder`）

**文件**: `code/platform-server/platform-common/src/main/java/com/cloudhub/platform/common/config/TenantContextHolder.java` (15 行)

```java
public class TenantContextHolder {
    private static final ThreadLocal<Long> TENANT_ID = new ThreadLocal<>();
    private static final ThreadLocal<Long> USER_ID = new ThreadLocal<>();
    // set/get/clear 方法省略
}
```

- ✅ 提供 `setTenantId / getTenantId / setUserId / getUserId / clear`
- ✅ 请求结束由 Filter 调 `clear()` 清理，避免线程复用污染

### 2.2 HTTP 过滤器（替代 HandlerInterceptor）

**文件**: `code/platform-server/platform-common/src/main/java/com/cloudhub/platform/common/config/TenantFilter.java` (39 行)

**关键点**:
- 继承 `OncePerRequestFilter`（Spring 内置保证每个请求只跑一次）
- 从 `Authorization: Bearer <token>` 解 JWT（`JwtUtil.getUserId` + `JwtUtil.getTenantId`）
- 写入 ThreadLocal → 业务代码可读
- `finally` 块 `clear()`，避免内存泄漏

**与主规划 5.1.2 Step 2 差异**:
- 主规划方案用 `HandlerInterceptor + WebMvcConfigurer.addInterceptors`
- 实际用 `OncePerRequestFilter`（Servlet Filter 层，**比 Interceptor 早**）
- **理由**: Filter 在所有 MVC 处理之前执行，可拦截静态资源 / Actuator / 错误页；Interceptor 仅作用于 Controller
- **评价**: ✅ **优于主规划方案**，无需追加 WebConfig

### 2.3 MyBatis-Plus 拦截器（核心）

**文件**: `code/platform-server/platform-common/src/main/java/com/cloudhub/platform/common/config/MybatisPlusConfig.java` (95 行)

**关键 Bean**:

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(new TenantLineHandler() {
        @Override
        public Expression getTenantId() {
            Long tenantId = TenantContextHolder.getTenantId();
            return tenantId != null ? new LongValue(tenantId) : new LongValue(1);
        }

        @Override
        public boolean ignoreTable(String tableName) {
            Long tenantId = TenantContextHolder.getTenantId();
            if (tenantId == null) return true;  // 无租户上下文不拼接
            return IGNORE_TABLES.contains(tableName);
        }
    }));
    interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
    return interceptor;
}
```

**与主规划 5.1.2 Step 3 差异**:

| 主规划 | 实际 | 评价 |
|------|------|------|
| `return new LongValue(TenantContext.get());` | `tenantId != null ? new LongValue(tenantId) : new LongValue(1)` | ✅ 更稳健：上下文为空时默认 1（兼容后台任务） |
| `return IGNORE_TABLES.contains(...)` | 多了 `tenantId == null → return true` | ✅ **更安全**：无上下文时**不拼接**租户条件，避免数据"全租户混合返回"事故 |

## 六、决策日志

### 6.1 为什么是 `OncePerRequestFilter` 而不是 `HandlerInterceptor`？

| 候选 | 优劣 |
|------|------|
| **HandlerInterceptor**（主规划原方案） | 优点：与 Spring MVC 集成度高；缺点：仅拦截 Controller，**Actuator / 错误页 / 静态资源** 无租户隔离 |
| **OncePerRequestFilter**（实际方案） | 优点：Servlet 容器级，**所有请求**都拦截；缺点：低 level 不能直接访问 HandlerMethod |
| Spring Security Filter | 优点：功能强大；缺点：**当前未引入 Spring Security**，引入成本高 |

**决策**: 用 `OncePerRequestFilter`。理由是**安全优先**（拦截范围最大），且**与 Spring Security 解耦**（不强依赖）。

### 6.2 为什么 `sys_oper_log` / `sys_login_log` 的 tenant_id 默认值是 0 而非 1？

观察: V16 迁移用了 `DEFAULT 0`，其他表用 `DEFAULT 1`。

**可能原因**:
- 这两张表是**审计日志**，历史数据可能是无租户上下文下写入的（如定时任务）
- `0 = 平台级 / 无租户归属` 的语义

**风险**:
- 如果未来查询"租户 1 的操作日志"会漏掉 DEFAULT 0 的历史数据
- 但这与"跨租户收集审计日志便于排障"的设计原则一致

**待办**（不在本审计范围）: 确认是否应该有默认值不一致的规则文档。

### 6.3 IGNORE_TABLES 为什么是硬编码而不是 Nacos 动态配置？

**当前**: 19 个表名硬编码在 `MybatisPlusConfig.java:24-33`

**优势**:
- 启动期一次性确定，无运行时变更风险
- 无需 `@RefreshScope`，避免热加载带来的 SQL 行为漂移

**劣势**:
- 新增业务表时**需要改代码 + 重新发版**
- 紧急情况（如发现某表漏配）无法秒级回滚

**决策**: 当前**保留硬编码**，但**新增回滚开关文档** `P0-1-回滚开关设计.md` 解决"紧急回滚"诉求（关掉整个拦截器 = 回到 v3.1 之前行为）。
