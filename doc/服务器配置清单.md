### 1.4 适用场景

- ✅ 单人开发 / POC / 客户演示
- ✅ 内部小团队 (< 10 人), 流量 < 50 QPS
- ✅ CI/CD runner (跑测试)
- ❌ 生产环境 (单点故障, 无 HA)
- ❌ 高并发场景 (> 200 QPS)
- ❌ 7x24 业务 (SLA 99.9% 难以保障)

### 1.5 升级到生产的触发条件

- 业务 SLA 要求 > 99.5% (月停机 < 3.6 小时)
- 峰值 QPS > 200
- 用户数 > 1000 并发
- 多团队独立部署需求
- 跨可用区/机房容灾需求

**满足任一即应升级到 §二 生产环境**。

## 二、生产环境 (3 节点 HA, 500 高并发 + 24/7)

> **设计目标**:
> - **500 并发用户** (峰值 ~1500 req/sec, 假设平均响应 200ms, 留 2x 突发余量)
> - **99.9% SLA** (月停机 < 43 分钟, 全年 < 4.4 小时)
> - **24/7 不间断运行** (滚动更新、故障自动转移、零停机部署)
> - **多 AZ 防机房级故障** (云上跨可用区, 自建跨机柜)

### 2.1 硬件推荐 (3 节点, 统一规格, 便于 K8s 调度)

> **避免浪费原则**: 基于 217 单机实测 6 核 14GB 跑 22 服务, 3 节点 HA 需覆盖 2x 副本 + 50% 增长 = 总资源约 9x 217。
> 但 500 并发不需要 9x 资源 (1 核可处理 200 QPS 简单 CRUD), **右-sized 给出 3x 12c48g**, 总 36 核 144GB。

| 配置项 | 单节点 | 集群合计 (3 节点) | 说明 |
|--------|--------|---------------------|------|
| **CPU** | **12 核** (Xeon 银牌 4310 或同等) | 36 核 | 留 4 核给 OS + 监控, 8 核给业务 |
| **内存** | **48 GB** DDR4 ECC | 144 GB | 含 8 GB headroom, 不浪费 |
| **系统盘** | 200 GB NVMe SSD | 600 GB | OS + Docker/K8s 运行时 |
| **数据盘** | 1 TB NVMe SSD | 3 TB | 数据库/ES/Kafka 数据 |
| **备份盘** | 1 TB (可挂 NAS 替代) | - | 全量备份 + binlog |
| **网络** | 10 Gbps 内网 + 1 Gbps 公网 | - | 节点间同步流量大, 公网入口走 SLB |

## 三、组件 HA 详解 (含 RTO / RPO)

> **RTO** (Recovery Time Objective): 故障后恢复服务的目标时间
> **RPO** (Recovery Point Objective): 故障后可容忍的数据丢失窗口

### 3.1 MySQL 主从 + 灾备

**拓扑**: 1 Primary + 2 Replicas (各节点 1 实例)
```
[Node-1: mysql-primary]  ─── 同步复制 ──→  [Node-2: mysql-replica-1]
       │                            ╲──── 异步 ──→  [Node-3: mysql-replica-2]
       │                                            (read-only, 可拆出做 BI 查询)
       ↓
   业务写入
```

**复制方式**:
- **方案 A (推荐)**: Group Replication (MGR) 单主模式
  - 自动选主, RPO=0 (同步)
  - RTO < 30s (自动)
  - 需 MySQL 5.7.17+ / 8.0+
- **方案 B (备选)**: Semi-sync Replication + MHA/Orchestrator
  - 半同步, RPO < 1s
  - RTO 30s-2min (需 Orchestrator 触发)
  - 工具成熟, MySQL 5.5+ 即可

**HA 方案选型**:
| 场景 | 推荐 | 备注 |
|------|------|------|
| **自建 (3 节点物理机)** | MGR 单主 | 内置 HA, 无外部依赖 |
| **自建 (云上虚拟机)** | Orchestrator + Semi-sync | 成熟, 文档多 |
| **托管** | **阿里云 RDS MySQL 高可用版 / 腾讯云 MySQL 双机** | **最省心, 自动备份+主备切换**, 月费 +800 元 |

**RTO / RPO 目标**:
| 故障场景 | RTO | RPO | 应对 |
|----------|-----|-----|------|
| 主库进程崩溃 | 30s (MGR) | 0 | MGR 自动选新主 |
| 主库硬件故障 | 30s | 0 | MGR 自动选新主 (replica 升主) |
| 节点 1 整机故障 | 30s | 0 | 副本 1 升主, 业务继续 |
| 误操作 (DROP) | 1-24h (取决于备份频率) | 分钟级-小时级 | 备份恢复 |
| **机房级故障 (云 AZ 故障)** | **30min-2h** (切换 DR) | **< 1min** (异地 binlog 同步) | 启动 DR 站 |

**灾备 (DR) 方案**:
1. **异地 binlog 实时同步**: 通过 DTS / DRC 工具同步到异地 MySQL
2. **每日全量备份**: `mysqldump` → OSS/S3, 保留 30 天
3. **季度恢复演练**: 实际在 DR 站跑 `mysqldump` 恢复, 测 RTO

### 3.2 Redis Sentinel (3 节点)

**拓扑**: 1 Redis Master + 2 Replicas + 3 Sentinel 节点
```
[Node-1] Redis-Primary + Sentinel-1
[Node-2] Redis-Replica-1 + Sentinel-2
[Node-3] Redis-Replica-2 + Sentinel-3
```

**HA 行为**:
- Sentinel 集群监控主库, 主观下线 (PFAIL) → 客观下线 (ODOWN) → 选新主 (Raft 协议)
- **RTO**: 5-30s (sdown → failover 完成)
- **RPO**: 0 (复制是同步的, replica 升主时数据已一致)

**为什么不选 Redis Cluster**: Cluster 用于 > 100K ops/sec 或需要 sharding, 本项目 ~5-10K ops/sec, Sentinel 简单 10 倍。

**资源**:
- maxmemory 4 GB per node (maxmemory-policy allkeys-lru)
- 留 50% buffer: 容器 limits 8 GB

### 3.3 Kafka 集群 (3 节点, KRaft)

**拓扑**: 3 Brokers (KRaft 模式, 无 Zookeeper)
```
[Node-1] Kafka-Broker-1
[Node-2] Kafka-Broker-2
[Node-3] Kafka-Broker-3
```

**HA 行为**:
- Topic partition 的 leader 故障 → controller 选新 leader (~5s)
- producer 设置 `acks=all` + `min.insync.replicas=2` → **RPO = 0** (至少 2 副本写入才算成功)
- **RTO**: < 30s (broker 故障 + controller 选新 leader)

**关键配置**:
```properties
# broker 配置
process.roles=broker,controller
node.id=1  # 2, 3
controller.quorum.voters=1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093
offsets.topic.replication.factor=3
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2
default.replication.factor=3
min.insync.replicas=2
```

**资源**: 4 GB heap per broker + page cache (8-16 GB OS cache 留给 Kafka, 用 SSD 磁盘)

### 3.4 Elasticsearch 集群 (3 节点)

**拓扑**: 3 Master-eligible + 3 Data (or 3 节点合 1 master-eligible + 2 data)
```
[Node-1] ES-node-1 (master-eligible + data)
[Node-2] ES-node-2 (master-eligible + data)
[Node-3] ES-node-3 (master-eligible + data)
```

**HA 行为**:
- master 故障 → 选新 master (~3s)
- shard primary 故障 → replica 升 primary (~1s)
- **RTO**: < 30s
- **RPO**: 0 (replication 是同步的, 默认 sync)

**关键配置**:
```yaml
discovery.seed_hosts: ["es-node-1", "es-node-2", "es-node-3"]
cluster.initial_master_nodes: ["es-node-1", "es-node-2", "es-node-3"]
discovery.zen.minimum_master_nodes: 2  # 防脑裂 (3 节点时配 2)
xpack.security.enabled: true  # 生产必须开
xpack.security.transport.ssl.enabled: true
xpack.security.http.ssl.enabled: true
```

**shard 规划** (按业务量):
- 单个 index (如 platform-logs) 主分片数 = 节点数 = 3
- 副本数 = 1 (3 节点时足够, 数据冗余 + 1 节点故障可用)
- 总 shard 数 = 3 主 + 3 副本 = 6 (符合 ES 建议 < 100 shards/节点)

**资源**: 4 GB heap per node, **JVM heap ≤ 31 GB (ES 硬性限制)**, **heap ≤ 物理内存一半**

### 3.5 Nacos 集群 (3 节点)

**拓扑**: 3 Nacos 节点, 共享外部 MySQL
```
[Node-1] Nacos-1
[Node-2] Nacos-2
[Node-3] Nacos-3
     ↓
[MySQL platform_nacos]  # 共享, 数据持久化
```

**HA 行为**:
- Nacos 节点故障 → 客户端连其他节点, 服务发现无中断
- 配置变更 → 通过 Distro 协议同步到所有节点
- **RTO**: < 5s (客户端重连)
- **RPO**: 0 (MySQL 持久化)

**资源**: 1 GB heap per node (够用, 多数场景 < 500 MB)

### 3.6 MinIO 分布式 ⚠️

> **重要**: MinIO **生产推荐 4 节点最小** (EC:2 模式需要 4 节点)。3 节点需要用 Distributed Mode + replication, 牺牲 EC 的空间效率。

**方案 A (推荐, 4 节点)**: 扩到 4 节点
- Erasure Coding 4+2: 数据 4 块 + 校验 2 块, **可用 67% 容量, 容 2 节点故障**
- 单节点 1 TB → 集群 2.7 TB 有效

**方案 B (3 节点妥协)**: Distributed Mode + RF=2
- 每个对象存 2 份
- **可用 50% 容量, 容 1 节点故障**
- 单节点 1 TB → 集群 1.5 TB 有效

**选型建议**: **业务量大/文件多时选方案 A** (扩到 4 节点), **小规模用方案 B 凑合** (3 节点), 实际推荐方案 A。

### 3.7 后端服务 (K8s Deployment 2+ 副本)

**HA 行为**:
- Pod 故障 → K8s 自动重启
- 节点故障 → Pod 在其他节点重建 (~30s)
- 滚动更新 → 旧 Pod 优雅关闭 (Spring Boot graceful shutdown), 新 Pod 启动, **零停机**

**关键 K8s 配置**:
```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 2  # 至少 2, 关键服务 (gateway, user) 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0  # 零停机关键
      maxSurge: 1
  template:
    spec:
      containers:
      - name: platform-gateway
        readinessProbe:  # K8s 用, 比 docker healthcheck 更准
          httpGet: { path: /actuator/health/readiness, port: 8083 }
          periodSeconds: 5
        livenessProbe:  # 探活, 失败则重启
          httpGet: { path: /actuator/health/liveness, port: 8083 }
          periodSeconds: 10
      topologySpreadConstraints:  # 反亲和性, 副本分散到 3 节点
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: DoNotSchedule
```

## 四、数据库灾备 (DR) 方案

### 4.1 MySQL 灾备

**方案**:
1. **同城异 AZ 实时 binlog 同步** (阿里云 DTS / 自建 canal / DRD)
   - RPO: < 1s
   - 切换时 RTO: 30 min (人工 + DNS 切换)
2. **异地冷备** (每日全量 + binlog)
   - 阿里云 OSS / AWS S3 跨 region
   - 保留 30 天
   - 恢复 RTO: 1-4h (取决于数据量)

**备份脚本** (生产 cron):
```bash
# 每日 02:00 全量
0 2 * * * /opt/scripts/backup-mysql-full.sh
# 持续 binlog 归档
*/5 * * * * /opt/scripts/archive-binlog.sh

# /opt/scripts/backup-mysql-full.sh
#!/bin/bash
TS=$(date +%Y%m%d_%H%M%S)
mysqldump -h mysql-primary --single-transaction --master-data=2 \
  --all-databases | gzip > /backup/mysql/full_$TS.sql.gz
aws s3 cp /backup/mysql/full_$TS.sql.gz s3://my-bucket/mysql/
find /backup/mysql -name "full_*.sql.gz" -mtime +30 -delete
```

### 4.2 Elasticsearch 灾备

**方案**:
1. **每日 snapshot 到 OSS/S3**: `PUT /_snapshot/my_backup`

3. **ILM 自动管理**: 7-30 天后自动删, 不撑爆磁盘

### 5.4 关键 JVM 通用参数 (生产 500 并发必加)

所有 platform-* 服务 JAVA_OPTS 追加:
```bash
-XX:MaxRAMPercentage=70.0        # 容器内存的 70% 作为 heap (K8s 资源限制下自动)
-XX:+UseContainerSupport         # JDK 11+ 识别 cgroup 限制 (关键!)
-XX:+UseG1GC                     # 低延迟 GC (Web 场景)
-XX:+ParallelRefProcEnabled      # 并行处理引用, 缩短 STW
-XX:MaxGCPauseMillis=100         # 目标 GC 暂停 ≤ 100ms
-Djava.security.egd=file:/dev/./urandom  # 加快启动
```

修改位置: `docker-compose.yml` 每个 platform-* 服务的 `JAVA_OPTS` 末尾追加 (或在 K8s 用 `JAVA_TOOL_OPTIONS` 统一注入)。
