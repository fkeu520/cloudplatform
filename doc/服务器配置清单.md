## 一、单节点部署（开发/演示环境）

单机部署所有服务，适用于 POC、演示、小规模内部使用。

| 配置项 | 最低可用 | 推荐 | 说明 |
|--------|---------|------|------|
| **CPU** | 8 核 | 16 核 | 中间件+后端服务并发启动需多核 |
| **内存** | 32 GB | 64 GB | ES 独占 4G，MySQL 4G，后端服务 x6 共约 6G |
| **系统盘** | 100 GB | 200 GB | 操作系统 + Docker 镜像存储 |
| **数据盘** | 200 GB | 500 GB | MySQL 数据、ES 索引、MinIO 文件存储 |
| **网络** | 100 Mbps | 1 Gbps | |

> **L1 + L2 优化**: 实施 [`L2_Spring精简优化方案.md`](L2_Spring精简优化方案.md) 后内存可大幅压缩。详见下方"L1+L2 优化后配置"小节。

### L1+L2 优化后配置（推荐）

实施 [`L2_Spring精简优化方案.md`](L2_Spring精简优化方案.md) 后，6 个 platform-* 服务总内存从 **5.7GB → 2.2GB（-61%）**，整体余量大幅提升：

| 配置项 | 最低可用 (L2 后) | 推荐 (L2 后) | 说明 |
|--------|---------|------|------|
| **CPU** | 4 核（仅 dev）| 8 核 | L2 后业务负载 CPU 主导 |
| **内存** | 16 GB | 32 GB | platform-* 从 5.7GB → 2.2GB，**余量 6GB+** |
| **系统盘** | 100 GB | 200 GB | 同上 |
| **数据盘** | 200 GB | 500 GB | 同上 |
| **网络** | 100 Mbps | 1 Gbps | 同上 |

## 二、3 节点高可用集群

适用于生产环境。每个节点配置相同，服务分布如下：

### 节点角色

| 节点 | 职责 | 部署服务 |
|------|------|---------|
| **Node-1** | 控制 + 业务 | gateway, auth, user, workflow, message, ops + 前端 |
| **Node-2** | 数据 + 业务 | MySQL/RDS 备, ES 数据, Kafka, MinIO, 部分后端 |
| **Node-3** | 协调 + 观察 | Nacos 集群, ES 主, Kibana, Logstash, XXL-JOB |

> 实际 K8s 环境下通过亲和性/反亲和性调度，此处按物理节点做职责划分。

### 配置清单

#### 方案 A：最低可用（勉强跑，不推荐生产）

| 配置项 | 每节点规格 | 集群合计 |
|--------|-----------|---------|
| **CPU** | 8 核 | 24 核 |
| **内存** | 32 GB | 96 GB |
| **系统盘** | 100 GB (SSD) | 300 GB |
| **数据盘** | 500 GB (SSD) | 1.5 TB |
| **网络** | 1 Gbps | - |

**风险**：内存紧张，ES 和 MySQL 争抢资源，高并发下容易 OOM。

#### 方案 B：推荐配置 ✅

| 配置项 | 每节点规格 | 集群合计 |
|--------|-----------|---------|
| **CPU** | 16 核 | 48 核 |
| **内存** | 64 GB | 192 GB |
| **系统盘** | 200 GB (NVMe SSD) | 600 GB |
| **数据盘** | 1 TB (NVMe SSD) | 3 TB |
| **网络** | 10 Gbps | - |

#### 方案 C：高性能配置

| 配置项 | 每节点规格 | 集群合计 |
|--------|-----------|---------|
| **CPU** | 32 核 | 96 核 |
| **内存** | 128 GB | 384 GB |
| **系统盘** | 500 GB (NVMe SSD) | 1.5 TB |

## 三、高可用部署架构

```
                         ┌──────────────┐
                         │   SLB / Nginx │
                         │   (负载均衡)   │
                         └──────┬───────┘
                                │
                  ┌─────────────┼─────────────┐
                  │             │             │
           ┌──────┴──────┐ ┌───┴───────┐ ┌───┴──────┐
           │   Node-1     │ │  Node-2   │ │  Node-3  │
           │              │ │           │ │          │
           │  gateway x2  │ │  user x2  │ │  nacos   │
           │  auth x2     │ │  workflow │ │  ES(master)
           │  admin/ops   │ │  message  │ │  kibana  │
           │  nginx       │ │  ops x2   │ │  logstash│
           │              │ │  mysql M  │ │  xxl-job │
           └──────────────┘ └───────────┘ └──────────┘
```

### 关键组件 HA 方案

| 组件 | 高可用策略 | 节点分布 |
|------|-----------|---------|
| **MySQL** | 主从复制 / 半同步 / 可换 RDS | 2 节点主备 |
| **Redis** | 哨兵模式 3 节点 / 可换外部 | 3 节点 |
| **Kafka** | 3 节点 KRaft 模式 | 3 节点 |
| **ES** | 3 节点集群 (主+数据) | 3 节点 |
| **Nacos** | 3 节点集群 | 3 节点 |
| **后端服务** | Deployment 2+ 副本 | 跨节点分布 |
| **MinIO** | Erasure Coding 4+2 | 3 节点 |
| **Nginx** | Keepalived + 主备 | 2 节点 |

## 五、注意事项

1. **MySQL 建议用云 RDS**：自建 MySQL 做 HA 麻烦，RDS 自带主备+自动故障切换
2. **Redis 建议用云 Redis**：同样理由，云 Redis 自带哨兵/集群
3. **ES 堆内存**：ES 的 JVM 堆不要超过 31G，且堆大小 = 物理内存一半（推荐 16G 堆 / 32G 总内存）
4. **Kafka 磁盘**：Kafka 对磁盘吞吐要求高，建议 NVMe SSD；消息保留时间建议 3 天以内
5. **Docker 数据目录**：确保 Docker 数据目录在数据盘，不要占用系统盘
6. **日志清理**：ES 索引 ILM 设置 7-30 天自动删除，避免日志撑爆磁盘
