## 教训沉淀
1. **Flyway V36 同表 DELETE 限制**：MySQL 不允许 DELETE/UPDATE 的子查询直接引用被修改的表，必须用派生表包一层 `(SELECT ... FROM (SELECT ...) AS _alias)`。这是个反复踩的坑，已在 KNOWN_ISSUES 中见过类似问题。
2. **Flyway 失败后启动循环**：失败迁移会在 `flyway_schema_history` 留 `success=0` 记录，下次启动拒绝重跑。修复方式：要么手动 `UPDATE success=1` 标记已应用，要么 `DELETE` 该记录让 Flyway 重跑修复版 SQL。`platform-user` 等核心服务挂了影响范围很大（登录/用户/菜单全挂），要第一时间恢复。
3. **V36 INSERT IGNORE 200/201 与 V29 冲突**：V29 已用 200/201 表示 物业管理/楼宇列表，V36 想用 200/201 表示 房源管理/园区管理。`INSERT IGNORE` 静默保留旧值导致 V36 看似成功但菜单名没改。**新 migration 应先 SELECT 检查再用 UPDATE 或用新 ID 范围**。
4. **docker exec 中文编码**：通过 SSH + docker exec -i 传递包含中文的 SQL 时，PowerShell 的 `rtk read` 中转会丢字符。解决：用 `scp` 上传 UTF-8 文件 + `docker exec -i mysql --default-character-set=utf8mb4`。
5. **image 升级但容器未重启**：`docker compose pull + up -d` 在新 image digest 与旧 digest 相同时不会 recreate。强制用 `--force-recreate`。
