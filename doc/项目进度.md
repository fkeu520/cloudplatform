### 🔴 P1 — 多机部署前必须修复

#### 1. MyBatis-Plus workerId/datacenterId 未显式配置  ✅ **已修复并验证**
- **现状（修复前）**：`application.yml` 仅配置 `id-type: assign_id`，未设置 `worker-id` / `datacenter-id`
- **默认行为**：MP 3.5.5 `DefaultIdentifierGenerator` 从容器 MAC 地址和 IP 哈希派生 → 单机部署下所有服务拿到**相同的 workerId+datacenterId**
- **风险**：
  - 单机部署：每 JVM 独立 sequence 计数器（12 位 = 4096/ms），单服务 ≤ 4096 inserts/ms 安全，多服务并发总和若超 4096/ms 会碰撞
  - **多机部署**：两台机器的 MAC/IP 不同 → 派生不同的 workerId → 看似无碰撞，但如果两机时钟回拨或 NTP 漂移会导致 ID 异常

**修复 (2026-06-02)**:
- `MybatisPlusConfig.java` 新增 `@Bean IdentifierGenerator identifierGenerator(...)`,通过 `@Value` 读取 yml `mybatis-plus.snowflake.worker-id/datacenter-id`,校验 0-31 范围
- 5 个服务 yml 加 snowflake 配置:`${MYBATIS_PLUS_SNOWFLAKE_WORKER_ID:N}` 支持环境变量覆盖
- `docker-compose.yml` 注入差异化 env vars

**服务分配**:
| 服务 | workerId | datacenterId |
|------|----------|--------------|
| platform-user | 1 | 1 |
| platform-ops | 4 | 1 |
| platform-message | 1 | 2 |
| platform-workflow | n/a (无 @TableId) | n/a |
| platform-auth | n/a (无 mybatis-plus 依赖) | n/a |

**E2E 验证 (3/3 服务通过)**:
| 服务 | 雪花 ID | 二进制提取 datacenter / worker | 结果 |
|------|--------|--------------------------------|------|
| platform-user | dept `2061637441810468865` | datacenter=1, worker=1 | ✅ PASS |
| platform-user | post `2061637448580075522` | datacenter=1, worker=1 | ✅ PASS |
| platform-ops | tenant `2061638768712105986` | datacenter=1, worker=4 | ✅ PASS |
| platform-message | channel `2061639325447360514` | datacenter=2, worker=1 | ✅ PASS |

### 🟡 P2 — 环境/基础设施已知问题

#### 3. Gateway Nacos 间歇启动失败  ✅ **已修复并真场景验证**
- **症状**：容器启动时 Nacos 还未就绪 → `Client not connected, current status:STARTING` → `webServerStartStop` bean 失败 → web server 未监听 8083
- **触发条件**：Docker Desktop 重启后第一次启动 gateway 容器
- **当前缓解**：`docker restart platform-gateway` 后 33s 启动成功

**修复 (2026-06-02, 采用方案 A + 增强 B)**:
- 5 个服务 yml 加 `spring.cloud.nacos.discovery.fail-fast: false`
- Nacos healthcheck 增强为 `HTTP 8848` + `gRPC 9848` 双端口测试(9848 是 gRPC 真正用于服务注册/订阅的端口,只测 8848 不足以判断 Nacos 是否就绪)
- 部署后所有 6 个后端服务 + Nacos `healthy`,服务在 Nacos 启动慢于服务启动顺序时不再阻塞

**v6.5 真场景验证 (新增)**:
- 测试方法: 模拟 Docker Desktop 重启场景,停 Nacos 后重启 gateway
- 步骤: `docker stop platform-nacos` → `docker restart platform-gateway` → 观察 60s → `docker start platform-nacos` → 观察 60s
- 结果:
  - gateway 在 Nacos 关闭时启动,`Up 6s` → `Up 57s (health: starting)`,**未崩溃**
  - `/actuator/health` 返回 503 (Nacos health indicator DOWN, 服务本身 UP, port 8083 正常监听)
  - Nacos 恢复后 60s `healthy`, HTTP 8848 返回 200
  - gateway 自动重连: log `Grpc connection connect` @ T+106s
  - 自动重新注册: log `Redo instance operation REGISTER for DEFAULT_GROUP@@platform-gateway` @ T+109s
  - 最终状态: gateway `(healthy)`, `/actuator/health` → `{"status":"UP"}`
- **结论**: `fail-fast=false` 修复完全生效,服务在 Nacos 不可用期间保持 UP,恢复后自动重连注册,零人工干预。

### P0: Spring Cloud Gateway 鉴权失败响应丢失修复

**症状**: 经 gateway 8083 的所有需鉴权 API 返回 `HTTP/1.1 200 + Content-Length: 0` (前端无法识别未鉴权状态)
