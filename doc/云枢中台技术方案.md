## 1. 项目概述

### 1.1 背景

传统信息化建设存在以下痛点：

- **信息孤岛，运维效率低**：烟囱式系统部署，数据不共享，业务不联动
- **重复建设，资源浪费**：各业务线重复开发通用能力，缺乏统一技术底座
- **生态闭环缺失**：未形成应用、管理、分析、服务层面的生态闭环
- **扩展性低**：缺乏前瞻性规划，重复投资，无法平滑迭代

### 1.2 建设目标

构建通用技术底座，提供可复用的平台级能力：
- **一体**：统一技术底座作为数字化建设的基础支撑
- **两翼**：通用业务能力 + 数据服务能力
- **五大领域**：端、边、管、云、用全协同

### 1.3 核心价值

| 价值维度 | 说明 |
|---------|------|
| 数据互联互通 | 全面汇集不同系统数据，形成数据资产和洞察 |
| 共性沉淀共享 | 组件化资源复用，快速灵活构建业务形态 |
| 快速业务创新 | 敏捷响应市场，快速上线与迭代试错 |
| 数据智能洞察 | 自动化和智能化驱动业务创新 |
| 生态持续运营 | 打通生态扩展，保持开放融合 |

## 5. 安全架构

### 5.1 认证授权

- **统一认证**：OAuth 2.0 + JWT，支持单点登录 (SSO)
- **多因素认证**：密码 + 短信/邮箱/生物识别
- **权限模型**：RBAC + ABAC 混合模型
- **API 安全**：API Key + 签名验证 + 限流

### 5.2 数据安全

- **传输加密**：HTTPS/TLS 1.3
- **存储加密**：AES-256 数据加密
- **数据脱敏**：敏感信息脱敏展示
- **数据备份**：定时备份 + 异地容灾

### 5.3 应用安全

- **输入验证**：XSS/SQL 注入防护
- **文件安全**：文件类型校验 + 病毒扫描
- **安全审计**：操作日志 + 异常行为检测
- **漏洞扫描**：定期安全扫描 + 渗透测试

## 6. 开发规范

### 6.1 代码规范

- **Java**：遵循阿里巴巴 Java 开发手册
- **前端**：ESLint + Prettier 代码格式化
- **命名规范**：驼峰命名、语义化命名
- **注释规范**：Javadoc、关键逻辑注释

### 6.2 接口规范

- **RESTful**：遵循 RESTful API 设计规范
- **版本管理**：URL 版本号 `/api/v1/xxx`
- **响应格式**：统一响应结构 `{code, data, message}`
- **错误码**：统一错误码规范

### 6.3 数据库规范

- **表命名**：小写字母 + 下划线，`t_模块_业务`
- **字段命名**：小写字母 + 下划线
- **索引规范**：主键、外键、查询字段建索引
- **SQL 规范**：禁止 `SELECT *`、禁止子查询嵌套

## 7. API 网关韧性设计（v3.0 新增，对应主规划 P3-6）

### 7.1 设计目标

平台网关是唯一流量入口，必须具备：
- **细粒度熔断**: 按 downstream 服务隔离故障
- **细粒度重试**: 仅对幂等接口，避免重复副作用
- **滑动窗口限流**: 精确到秒级，保护下游
- **全链路超时**: 防止慢请求堆积
- **灰度路由**: 按租户/用户/版本切分流量
- **API 配额**: 租户/接口二维，防止滥用

### 7.2 技术选型

| 能力 | 选型 | 备注 |
|------|------|------|
| 熔断 | **Resilience4j** | Spring Cloud Circuit Breaker 默认实现 |
| 重试 | **Spring Cloud Gateway Retry filter** + 自定义指数退避 | 仅 GET / 幂等 POST |
| 限流 | **Redis + Lua 脚本**（滑动窗口）| 替代原 Redis 简单计数器 |
| 超时 | **Sentinel** 或 Resilience4j TimeLimiter | 配合 Hystrix 退役 |
| 灰度 | **Nacos 权重 + 自定义 RoutePredicateFactory** | 按 Header / Param 切分 |
| 配额 | **Redis 计数器 + 租户/接口 key** | 配额不足返回 429 + Retry-After |

### 7.3 熔断配置示例

```yaml
resilience4j:
  circuitbreaker:
    instances:
      platformUser:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 20
        minimum-number-of-calls: 10
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
      platformWorkflow:
        sliding-window-size: 50  # 流程审批可容忍更多失败
        failure-rate-threshold: 70
```

### 7.4 限流 Lua 脚本

```lua
-- 滑动窗口限流
-- KEYS[1] = 限流 key (如 rl:user:123:api:/workflow/instance/start)
-- ARGV[1] = 窗口大小（秒）ARGV[2] = 阈值
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = tonumber(redis.call('TIME')[1])
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
local count = redis.call('ZCARD', KEYS[1])
if count >= limit then
  return 0  -- 拒绝
end
redis.call('ZADD', KEYS[1], now, now .. ':' .. math.random())
redis.call('EXPIRE', KEYS[1], window)
return 1  -- 通过
```

## 8. 分布式事务 / 最终一致性（v3.0 新增，对应主规划 P3-7）

### 8.1 设计目标

解决跨服务调用的**状态不一致**风险：
- workflow 审批通过 → message 发送失败 → 用户收不到通知
- tenant 创建 → ops 初始化失败 → 新租户无法登录
- 任务分配 → user 服务查候选人失败 → 任务悬挂

### 8.2 方案对比

| 方案 | 复杂度 | 性能 | 适用场景 | 本项目采纳 |
|------|------|------|---------|----------|
| **2PC** | 高 | 阻塞严重 | 强一致要求 | ❌ 中台场景不适合 |
| **TCC** | 高 | 中 | 资金/库存 | ❌ 业务侵入大 |
| **Saga** | 中 | 中 | 长事务 | ⚠️ Flowable 已覆盖部分 |
| **本地消息表 + Outbox** | 低 | 高 | 90% 异步场景 | ✅ **采纳** |
| **Kafka 事务** | 中 | 中 | 流处理 | ❌ 运维复杂 |

### 8.3 Outbox 模式架构

```
┌─────────────┐  同事务写  ┌──────────────┐  定时扫  ┌──────────┐
│ 业务表       │ ────────→ │ outbox 表    │ ───────→ │  Kafka    │
│ (workflow)   │           │ (status=pending)│         │ (投递)   │
└─────────────┘           └──────────────┘         └──────────┘
                              │                          │
                              │ 失败 N 次               │ 消费
                              ▼                          ▼
                        ┌──────────┐              ┌──────────────┐
                        │ 死信表    │              │ message 服务  │
                        │ + 告警    │              │ (重试/降级)   │
                        └──────────┘              └──────────────┘
```

### 8.4 数据模型

```sql
CREATE TABLE outbox_message (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  topic VARCHAR(100) NOT NULL,           -- Kafka topic
  payload TEXT NOT NULL,                 -- 消息体 JSON
  status TINYINT DEFAULT 0,              -- 0=pending 1=sent 2=failed
  retry_count INT DEFAULT 0,
  next_retry_at DATETIME,                -- 指数退避
  error_msg TEXT,
  tenant_id BIGINT,
  business_key VARCHAR(100),             -- 防重复
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_status_next (status, next_retry_at)
);
```

### 8.5 实施位置

- `platform-common/outbox/`: 通用 Outbox 实体 + 定时任务
- `platform-workflow/.../service/`: 审批通过时同事务写 outbox
- `platform-message/.../consumer/`: 消费 outbox 转投 Kafka + 重试

### 8.6 关键决策

- **不引入 Seata**: 增加运维复杂度和潜在故障点
- **不引入 Kafka 事务**: 仍需管理事务状态，不如本地表直接
- **Outbox 消息键防重**: `business_key` 唯一约束防止重复投递

### 8.7 触发

- 优先级: 🟠 P3 韧性 中
- 实施: **Q4 2026 末启动**（M5 P0-2 data_scope 完成后）

## 9. 业务指标体系（v3.0 新增，对应主规划 P1-5）

### 9.1 设计目标

从"只有基础设施指标"演进到"业务健康度可观测"：
- 事故时能回答"影响多少用户"
- SLO 有可衡量的指标（如"审批 P99 < 5s"）
- 业务异常早期告警

### 9.2 指标分层

```
L1 基础设施: docker stats / JVM GC / DB 连接池
L2 应用指标: 接口 QPS / 错误率 / 延迟 (Actuator/Micrometer 默认)
L3 业务指标: 流程发起 / 任务完成 / 消息触达 / 租户活跃 ← 新增
L4 SLO 指标: 由 L3 聚合 (P99 审批时长 / 5xx 率) ← 新增
```

### 9.3 业务指标清单

| 指标名 | 类型 | 标签 | 告警阈值 |
|--------|------|------|---------|
| `workflow_started_total` | Counter | process=..., tenant=... | — |
| `task_completed_total` | Counter | process=..., outcome=approved/rejected | — |
| `task_completion_duration_seconds` | Timer | process=... | P99 > 30s |
| `message_sent_total` | Counter | channel=..., status=success/failed | 失败率 > 5% |
| `user_login_total` | Counter | tenant=..., status=success/failed | 失败率 > 10% |
| `api_call_total` | Counter | service=..., endpoint=..., status=2xx/4xx/5xx | 5xx > 1% |
| `tenant_count_active` | Gauge | — | — |
| `kafka_consumer_lag` | Gauge | topic=..., group=... | > 1000 |

### 9.4 实施模式

```java
@Service
public class WorkflowInstanceService {
  private final MeterRegistry meterRegistry;

  public void start(ProcessDefinitionKey key, ...) {
    Counter.builder("workflow_started_total")
      .tag("process", key.name())
      .tag("tenant", TenantContext.get())
      .register(meterRegistry)
      .increment();
    // 业务逻辑
  }
}
```

### 9.5 实施位置

- 每个 platform-* 服务加 `micrometer-registry-prometheus` 依赖
- `application.yml` 暴露 `/actuator/prometheus`
- Prometheus server 抓取（独立部署）
- Grafana 大盘: 业务指标 + 基础设施

### 9.6 告警分级

| 级别 | 触发 | 通知 |
|------|------|------|
| **P0** | 5xx 率 > 1% / 流程 P99 > 60s | 立即呼叫值班 |
| **P1** | 5xx 率 > 0.5% / 审批 P99 > 30s | Slack/钉钉 |
| **P2** | 消息失败率 > 5% / 慢查询 > 1s | 邮件日报 |

### 9.7 触发

- 优先级: 🟠 P1 可观测性 中
- 实施: **M6 启动时一并实施**（与 P1-1 链路追踪同步）
