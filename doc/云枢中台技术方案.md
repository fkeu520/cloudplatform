## 1. 项目概述

### 1.1 背景

传统信息化建设存在以下痛点：
- **信息孤岛，运维效率低**：烟囱式系统部署，数据不共享，业务不联动
- **重复建设，资源浪费**：各业务线重复开发通用能力，缺乏统一技术底座
- **生态闭环缺失**：未形成应用、管理、分析、服务层面的生态闭环
- **扩展性低**：缺乏前瞻性规划，重复投资，无法平滑迭代

### 1.2 建设目标

构建通用技术底座，提供可复用的平台级能力：
- **一体**：统一技术底座作为数字化建设的基础支撑
- **两翼**：通用业务能力 + 数据服务能力
- **五大领域**：端、边、管、云、用全协同

### 1.3 核心价值

| 价值维度 | 说明 |
|---------|------|
| 数据互联互通 | 全面汇集不同系统数据，形成数据资产和洞察 |
| 共性沉淀共享 | 组件化资源复用，快速灵活构建业务形态 |
| 快速业务创新 | 敏捷响应市场，快速上线与迭代试错 |
| 数据智能洞察 | 自动化和智能化驱动业务创新 |
| 生态持续运营 | 打通生态扩展，保持开放融合 |

### 5.2 数据安全

| 层级 | 当前状态 | 目标 |
|------|---------|------|
| **传输加密** | ✅ HTTPS/TLS 1.3 (Nginx 终止) | 保持 |
| **存储加密 - 数据库字段** | ❌ 未实现 | 敏感字段（手机号/身份证/银行卡）AES-256 加密，Q1 2027 |
| **存储加密 - 磁盘/备份** | ❌ 未实现 | MySQL TDE（透明数据加密），Q4 2026 |
| **传输加密 - 服务间** | ❌ 内部明文 | mTLS (Q4 2026 生产) |
| **数据脱敏** | ⚠️ 部分 | 通用脱敏注解 `@SensitiveField`（Q3 2026）|
| **数据备份** | ⚠️ 定时 | 增加异地容灾 (Q1 2027) |

**加密粒度决策**:
- **字段级加密** (Field-level): 保护高敏数据（密码、身份证、银行卡、手机号）
- **存储层加密** (Storage-level / TDE): 保护整库，防磁盘物理窃取
- **传输层加密** (Transport / mTLS): 防止中间人攻击
- 三层叠加：字段级 + TDE + mTLS = 防内鬼 + 防外贼 + 防窃听

### 6.2 接口规范（v3.1 强化 API 版本管理）

#### 6.2.1 URL 规范

```
https://api.cloudhub.com/{gateway-path}/{service}/{version}/{resource}

示例:
  GET    /api/v1/user/page              分页查询
  GET    /api/v1/user/{id}              详情
  POST   /api/v1/user                   创建
  PUT    /api/v1/user/{id}              更新
  DELETE /api/v1/user/{id}              删除
  POST   /api/v1/user/{id}/reset-pwd    操作子资源
```

**版本号规则**:
- 路径前缀 `/api/v{major}/` 表示**主版本**
- 主版本变更 = 破坏性 API 变更（不向后兼容）
- 次版本 = 新增功能（向后兼容），用 header `X-API-Version: 1.2`
- gateway 路由匹配规则: `Path=/api/v1/**, /api/v2/**`

#### 6.2.2 统一响应结构

```json
{
  "code": 0,                  // 业务码: 0=成功, 1xxx=业务错误, 5xxx=系统错误
  "message": "ok",            // i18n key 或默认中文
  "data": { ... },            // 业务数据
  "traceId": "abc123",        // 全链路追踪
  "timestamp": 1735689600000  // 服务端时间戳
}
```

#### 6.2.3 错误码规范（P1-2 实施）

| 段 | 范围 | 含义 |
|---|---|---|
| 0 | 0 | 成功 |
| 1xxx | 1000-1999 | 通用业务错误（参数/权限/资源） |
| 2xxx | 2000-2999 | 用户域 |
| 3xxx | 3000-3999 | 权限/组织域 |
| 4xxx | 4000-4999 | 流程/任务域 |
| 5xxx | 5000-5999 | 消息/通知域 |
| 9xxx | 9000-9999 | 系统错误 |

示例: `code=2401` = "用户已存在"，`code=5103` = "消息发送失败"

#### 6.2.4 幂等性

写操作支持 `Idempotency-Key` 请求头防重复：
```
POST /api/v1/workflow/instance/start
Headers: Idempotency-Key: 5f9b3c8a-1234-5678
```

## 8. API 网关韧性设计（v3.1 补全，对应主规划 P3-6）

### 8.1 设计目标

平台网关是唯一流量入口，必须具备：
- **细粒度熔断**: 按 downstream 服务隔离故障
- **细粒度重试**: 仅对幂等接口，避免重复副作用
- **滑动窗口限流**: 精确到秒级，保护下游
- **全链路超时**: 防止慢请求堆积
- **灰度路由**: 按租户/用户/版本切分流量
- **API 配额**: 租户/接口二维，防止滥用
- **降级响应**: 熔断后返回兜底数据或友好错误码（v3.1 补）

### 8.2 技术选型

| 能力 | 选型 | 版本 | 备注 |
|------|------|------|------|
| 熔断 | **Resilience4j** | 2.2.0 | Spring Cloud Circuit Breaker 默认实现 |
| 重试 | **Spring Cloud Gateway Retry filter** | - | + 自定义指数退避 |
| 限流 | **Redis + Lua 脚本** | Redis 7 | 滑动窗口 |
| 超时 | **Resilience4j TimeLimiter** | 2.2.0 | 配合 mTLS 标识 |
| 灰度 | **Nacos 权重 + 自定义 RoutePredicateFactory** | - | 按 Header / Param 切分 |
| 配额 | **Redis 计数器 + 租户/接口 key** | Redis 7 | 配额不足返回 429 |

### 8.3 全链路超时传递（v3.1 补）

**问题**: 浏览器设了 30s 超时，但 gateway → user → workflow 各自有不同超时，**总链路不可控**。

**方案**: 通过 `X-Request-Timeout` 头逐跳传递

```
Browser (30s) → Gateway (28s) → user (15s) → workflow (5s)
                 ↑ X-Request-Timeout 减去已用时间
```

```yaml
# gateway application.yml
spring:
  cloud:
    gateway:
      httpclient:
        response-timeout: 28s   # 留 2s 给网关本身
```

```java
// WebClient 调用下游时
WebClient client = WebClient.builder()
    .filter((request, next) -> {
      long remaining = getRemainingTimeoutMs(request);
      return next.exchange(request.mutate()
        .header("X-Request-Timeout", remaining + "ms")
        .build());
    })
    .build();
```

### 8.4 重试白名单（v3.1 补）

**问题**: 自动重试可能造成**重复副作用**（如重复扣款、重复发短信）。

**方案**: 仅对**幂等接口**重试，白名单配置化

```yaml
# gateway application.yml
platform:
  gateway:
    retry:
      default-max-attempts: 1   # 默认不重试
      whitelist:                 # 幂等接口白名单
        - method: GET
          path-pattern: /api/v1/**   # 所有 GET 默认可重试
          max-attempts: 2
        - method: POST
          path-pattern: /api/v1/workflow/task/*/claim
          max-attempts: 1           # 签收不重试
        - method: POST
          path-pattern: /api/v1/auth/login
          max-attempts: 1           # 登录不重试
      blacklist:                 # 显式黑名单
        - method: POST
          path-pattern: /api/v1/message/send
        - method: POST
          path-pattern: /api/v1/workflow/instance/start
      # 未列白名单 → 走 default，不重试
      backoff:
        initial-interval: 500ms
        multiplier: 2
        max-interval: 5s
```

**判断标准**:
- GET/HEAD/OPTIONS → 默认可重试
- POST/PUT/DELETE → 必须有 `Idempotency-Key` 头或显式白名单才重试

### 8.5 熔断降级响应（v3.1 补）

**问题**: 熔断后默认返回 503 "Service Unavailable"，对用户不友好。

**方案**: 按服务配置降级响应

```yaml
resilience4j:
  circuitbreaker:
    instances:
      platformUser:
        sliding-window-size: 20
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
        fallback:
          # 降级策略（按降级等级）
          level: CACHED_OR_DEFAULT
          # 缓存命中: 读接口返回缓存的最后已知数据
          # 缓存未命中: 返回 defaultResponse
          default-response:
            code: 5001
            message: "用户服务暂时不可用，请稍后重试"
            data: null
      platformWorkflow:
        fallback:
          level: DEFAULT
          # 流程服务无缓存, 直接返回 default
          default-response:
            code: 5401
            message: "流程服务升级中，请稍后提交"
            data: null
      platformMessage:
        fallback:
          level: ASYNC_QUEUE
          # 消息服务熔断时, 写消息入本地队列, 服务恢复后补偿
          # 业务接口立即返回成功 (不阻塞主流程)
          async-queue: outbox
          default-response:
            code: 0
            message: "ok (消息已入队, 服务恢复后投递)"
            data: null
```

**降级等级**:
- `DEFAULT`: 直接返回兜底响应
- `CACHED_OR_DEFAULT`: 尝试本地缓存 → 兜底
- `STUB`: 返回桩数据（仅限查询）
- `ASYNC_QUEUE`: 写入本地队列，立即返回成功

### 8.6 熔断配置示例

```yaml
resilience4j:
  circuitbreaker:
    instances:
      platformUser:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 20
        minimum-number-of-calls: 10
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
      platformWorkflow:
        sliding-window-size: 50  # 流程审批可容忍更多失败
        failure-rate-threshold: 70
```

### 8.7 限流 Lua 脚本

```lua
-- KEYS[1] = 限流 key (如 rl:user:123:api:/workflow/instance/start)
-- ARGV[1] = 窗口大小（秒）ARGV[2] = 阈值
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = tonumber(redis.call('TIME')[1])
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
local count = redis.call('ZCARD', KEYS[1])
if count >= limit then
  return 0  -- 拒绝
end
redis.call('ZADD', KEYS[1], now, now .. ':' .. math.random())
redis.call('EXPIRE', KEYS[1], window)
return 1  -- 通过
```

## 9. 分布式事务 / 最终一致性（v3.1 补决策矩阵，对应主规划 P3-7）

### 9.1 设计目标

解决跨服务调用的**状态不一致**风险。

### 9.2 异步通信决策矩阵（v3.1 补）

| 场景 | 一致性要求 | 推荐方案 | 理由 |
|------|----------|---------|------|
| **业务通知**（审批通过发消息）| 强 | **Outbox 必用** | 丢消息 = 业务事故 |
| **租户初始化**（创建后初始化下游）| 强 | **Outbox 必用** | 不一致 = 业务不可用 |
| **任务分配**（候选查询）| 中 | **Outbox** 或**同步调用 + 重试** | 失败可重试 |
| **审计日志**（谁操作了什么）| 弱 | **Kafka 直接发** | 丢一条不影响业务 |
| **登录日志** | 弱 | **Kafka 直接发** | 同上 |
| **指标上报** | 弱 | **Kafka 直接发** | 丢指标可接受 |
| **缓存预热** | 弱 | **Kafka 直接发** | 缓存可重建 |
| **通知中心 UI 更新** | 弱 | **SSE 推送** | 用户没看到可刷新 |

**判断原则**:
- 失败会导致**业务事故** → Outbox
- 失败仅导致**数据缺失** → Kafka 直接发
- 失败会导致**用户体验差但可恢复** → 重试即可

### 9.3 Outbox vs 现有 Kafka 设计

**现状问题**:
- `WorkflowMessageProducer`（platform-workflow）直接调用 KafkaTemplate.send
- `MessageSendConsumer`（platform-message）消费后投递到渠道
- **问题**: workflow 业务事务提交后，Kafka 投递失败 → 消息丢失

**改造方案**:

```
现有:
  workflow 业务事务 ─┬─> 业务表写入
                     └─> KafkaTemplate.send()  ← 事务外, 可能丢
                          ↓
                     message 消费
                          ↓
                     渠道投递

改造后:
  workflow 业务事务 ─┬─> 业务表写入
                     └─> outbox 表写入 (同事务)
                          ↓ (定时任务)
                     outbox → Kafka (at-least-once)
                          ↓
                     message 消费（同前）
```

**改造工作量**:
- `platform-common`: 新增 `outbox_message` 表 + `OutboxPublisher` 定时任务
- `platform-workflow`: `WorkflowMessageProducer` 改为 `OutboxMessageWriter`
- `platform-message`: 保持现有 `MessageSendConsumer` 不变
- **兼容过渡**: 保留 `KafkaTemplate` 代码作为 fallback，配置开关切换

### 9.4 方案对比

| 方案 | 复杂度 | 性能 | 适用场景 | 本项目采纳 |
|------|------|------|---------|----------|
| **2PC** | 高 | 阻塞严重 | 强一致要求 | ❌ 中台场景不适合 |
| **TCC** | 高 | 中 | 资金/库存 | ❌ 业务侵入大 |
| **Saga** | 中 | 中 | 长事务 | ⚠️ Flowable 已覆盖部分 |
| **本地消息表 + Outbox** | 低 | 高 | 90% 异步场景 | ✅ **采纳** |
| **Kafka 事务** | 中 | 中 | 流处理 | ❌ 运维复杂 |

### 9.5 Outbox 模式架构

```
┌─────────────┐  同事务写  ┌──────────────┐  定时扫  ┌──────────┐
│ 业务表       │ ────────→ │ outbox 表    │ ───────→ │  Kafka    │
│ (workflow)   │           │ (status=pending)│         │ (投递)   │
└─────────────┘           └──────────────┘         └──────────┘
                              │                          │
                              │ 失败 N 次               │ 消费
                              ▼                          ▼
                        ┌──────────┐              ┌──────────────┐
                        │ 死信表    │              │ message 服务  │
                        │ + 告警    │              │ (重试/降级)   │
                        └──────────┘              └──────────────┘
```

### 9.6 数据模型

```sql
CREATE TABLE outbox_message (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  topic VARCHAR(100) NOT NULL,
  payload TEXT NOT NULL,
  status TINYINT DEFAULT 0,              -- 0=pending 1=sent 2=failed
  retry_count INT DEFAULT 0,
  next_retry_at DATETIME,
  error_msg TEXT,
  tenant_id BIGINT,
  business_key VARCHAR(100),             -- 防重复
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_status_next (status, next_retry_at)
);
```

### 9.7 实施位置

- `platform-common/outbox/`: 通用 Outbox 实体 + 定时任务
- `platform-workflow/.../service/`: 审批通过时同事务写 outbox
- `platform-message/.../consumer/`: 消费 outbox 转投 Kafka + 重试

### 9.8 关键决策

- **不引入 Seata**: 增加运维复杂度和潜在故障点
- **不引入 Kafka 事务**: 仍需管理事务状态，不如本地表直接
- **Outbox 消息键防重**: `business_key` 唯一约束防止重复投递

### 9.9 触发

- 优先级: 🟠 P3 韧性 中
- 实施: **Q4 2026 末启动**（M5 P0-2 data_scope 完成后）
