## 决策 1: 多角色 data_scope 合并策略 → A 取最严格

### 3 选 1

| 选项 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| **A. 取最严格** (scope 值大者) | `max(dataScope)` | 安全 (越严格越限) + 简单 | 误限 (用户应有权限被限) |
| B. 取并集 (OR 合并) | `dept_id IN (union)` | 灵活 | 复杂 SQL (多 union) |
| C. 主角色优先 | `role.isPrimary = true` | 简单 | 需新增字段 |

### 决策: A 取最严格

### 理由

1. **安全优先原则**: 与项目核心原则"可用性 > 可扩展性 > 性能"一致
   - "可扩展性"指"为未来留余地" — 误限可在应用层加白名单
   - "可误限"比"可越权"安全得多
2. **实现简单**: `max()` 一个数字即可, 无需复杂 SQL
3. **可逆性**: 误限可改回 scope=1 (最宽松) 而不需要重设计

### 风险

- **误限**: 用户具有多个角色, 最严格 role.data_scope 可能限制其应有权限
- **缓解**:
  - 默认 data_scope=1 (全部) 兼容老数据
  - 提供"运营管理后台"手动调整单用户 data_scope
  - 业务测试覆盖关键角色组合

### 实施 (TODO, M5-M2)

```java
// Aspect 实施 (伪代码)
int maxScope = scopes.stream()
    .map(UserRoleDataScope::getDataScope)
    .filter(Objects::nonNull)
    .max(Integer::compare)
    .orElse(1);
```

## 决策 2: dept 子树查询方案 → A 递归 CTE

### 3 选 1

| 选项 | 实现 | 性能 | 复杂度 |
|------|------|------|--------|
| **A. 递归 CTE** (MySQL 8.0+) | `WITH RECURSIVE` 单 SQL | 中 (与子树大小线性) | 低 (单 SQL) |
| B. 应用层递归 | Java 递归查 sys_dept | 慢 (N+1 查询) | 中 (多轮 IO) |
| C. 物化路径 (mpath) | 存 `path = "1/2/3/"`, LIKE 查询 | 快 (单次 IO) | 高 (需改造表结构) |

### 决策: A 递归 CTE

### 理由

1. **MySQL 8.0+ 已支持**: 项目使用 `mysql:8.0`, 无兼容性问题
2. **单 SQL 一次返回**: 不需 N+1 查询
3. **不需改造表结构**: 兼容现有 V1 树形 parent_id 设计
4. **代码可读**: `WITH RECURSIVE` SQL 清晰表达

### 风险

- **子树过大性能下降**: 万级子部门会慢 (但本项目租户 < 100, 部门 < 1000, 不存在)
- **MySQL 8.0 以下不兼容**: 项目锁定 MySQL 8.0, 无影响

### 实施 (TODO, M5-M2)

```sql
-- 递归查 user 所在部门的所有子部门 (scope=3)
WITH RECURSIVE dept_tree AS (
    SELECT id FROM sys_dept WHERE id = #{userDeptId}  -- 起点: 本部门
    UNION ALL
    SELECT d.id FROM sys_dept d
    INNER JOIN dept_tree dt ON d.parent_id = dt.id
)
SELECT id FROM dept_tree;
```

### 升级路径 (未来)

- 如果 dept 数 > 10 万: 升级 C 物化路径
- 改造 V23 migration: `ALTER TABLE sys_dept ADD COLUMN path VARCHAR(500)`
- 触发器维护 path
- LIKE 查询加速

## 决策 3: DataScopeInnerInterceptor 深度 → 基础版

### 决策: 基础版 (已实现)

### 当前实现

```java
// 基础版: PlainSelect + WHERE 拼接
public void beforePrepare(StatementHandler sh, Connection conn, Integer txTimeout) {
    String fragment = DataScopeContextHolder.get();
    if (fragment == null || fragment.isEmpty()) return;

    BoundSql boundSql = sh.getBoundSql();
    String originalSql = boundSql.getSql();
    String newSql = injectFragment(originalSql, fragment);
    // 反射设置新 SQL
}
```

### 已支持

- ✅ 简单 SELECT (PlainSelect)
- ✅ WHERE 子句追加 AND fragment
- ✅ 解析失败安全降级 (WARN 日志 + 放行原 SQL)
- ✅ MyBatis-Plus 自动配置 (在 mybatisPlusInterceptor Bean 中注册)

### 未支持 (留待 M5 完整业务化)

- ❌ UNION 查询
- ❌ 子查询嵌套
- ❌ 复杂 JOIN 多表条件
- ❌ UPDATE / DELETE 的 data_scope 拦截 (仅 SELECT)
- ❌ CTE WITH 子句的 data_scope 注入

### 理由: 业务简化

1. **99% 业务是简单 SELECT**: 列表查询 / 详情查询 / 分页查询
2. **复杂场景有 fallback**: 解析失败时**不抛异常**, 保留原 SQL, 业务可继续
3. **风险最低**: 基础版已可工作, 复杂场景逐步扩展

### 升级路径 (M5-M2 之后)

- **Phase 1 (M5-M2)**: 支持 UPDATE / DELETE 拦截
- **Phase 2 (M6)**: 支持 UNION / 子查询
- **Phase 3 (M7)**: 支持 CTE WITH

### 决策 2 修订: A 递归 CTE (修正实施)

**原 v1.0 决策**: A 递归 CTE (MySQL 8.0+)
**实际实施**: B 应用层递归 (`deptMapper.selectList(null)` 全表 + 内存 DFS)
**修订**: 实施修正为 A 递归 CTE, 决策与代码一致

**理由**:
1. 决策与实施必须一致, 长期偏离会造成"决策失效"印象
2. MySQL 8.0 已支持 `WITH RECURSIVE`, 无兼容性问题
3. CTE 单 SQL 一次返回, 不需加载全 dept 表
4. 显式 `tenant_id` 过滤 (顺带闭合缺口 #19)

**实施影响** (与缺口 #19 修复合并到 PR1):
- `UserDataScopeProviderImpl.collectChildDeptIds()` 重写为 CTE 查询
- 删除 `collectChildDeptIds` 应用层递归方法
- 新增 `selectChildDeptIdsByCte(rootDeptId, tenantId)` 方法
- 测试数据库需 MySQL 8.0+ (H2 测试环境用 mock 桩)
